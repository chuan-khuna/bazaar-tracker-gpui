# Implementation documents

How this project is built. Domain terms are defined in [GLOSSARY.md](../../GLOSSARY.md).

- [Bazaar Tracker manual](README.html) — the technical and user manual: what the app does, the prerequisites (Windows, Rust 1.92+, just, the game, the WebView2 Runtime), starting it (`just tracker run`, `just tracker build`, `just tracker start`, the single-instance rule), the window's panels and keys, how it works (`Player.log` plus game memory, a data-flow diagram, one Event from the game to the window, the startup steps, the background threads), how it stores data (where the data folder is on Windows and macOS, what the folder holds, `settings.toml`, `history.db` with WAL, schema backups and one writer at a time, logs, `art/`, data kept outside the folder, backing up, moving and clearing), checking against the live game, the tests, and troubleshooting.
- [Architecture](architecture.md) — the repo layout (a virtual workspace: the app in `apps/tracker`, the scrapers in `apps/scraper`, the Build Advisor in `apps/advisor`, the crates in `crates/`), the crate layout, layering rules, data folders and theme roles.
- [Modules](modules.md) — what each module in `crates/` and `apps/tracker/src/` does, and how an Event flows from the game to the window.
- [Data folder](data-folder.md) — where the app keeps its data, how to point a release build at the repo with `BAZAAR_TRACKER_DATA_DIR`, the `raw_data/` folder the scrapers fill for import, the `history.v<N>.bak.db` backups made before a migration, and the `art/` folder's layout.
- [Memory reading](memory-reading.md) — how the app reads the running game. `unityspy-rs`: read-only process access (`PROCESS_VM_READ | PROCESS_QUERY_LIMITED_INFORMATION`, exe `FileVersion` to Unity version), module and PE export lookup, the `mono_get_root_domain` check and assembly walk, the offset tables per Unity line (2021/2022 verified, 6000+ unverified, anything else an error), the class cache, fields up the parent chain, statics through the vtable, values by type code, BCL `List`/`Dictionary`/`HashSet`/`Nullable`, the `Memory` trait and `mono::testing`. `bazaar-tracker`: the `GameMemory` contract (`Ok(None)`, `Ok(Some)`, `Err`), `BazaarMemory`'s attach, reconnect and detach rules (500 ms ticks, optional classes retried every 5 s, detach after 5 failed board reads), the game classes and singletons behind each read, sorting cards into Board, Stash and skills, the rank scan, `Snapshot` and its parts, `FakeMemory`, `just tracker spike` and `just tracker snapshot`, and what to do after a game update.
- [Player.log](player-log.md) — where the game's log is (`LocalLow\Tempo Storm\The Bazaar`, the `log_path` setting, `just tracker track --log`), following it (500 ms polls from the end, a missing file waited for, truncation and replacement caught by a 256-byte tail signature, at most 16 MiB a pass, whole lines only), and parsing: the dropped timestamp, the substring guards before the regexes, and each `LogLine` variant with real example lines and near misses.
- [Run state machine](run-state-machine.md) — how `run/` and `tracker/` turn log lines and memory reads into Events: `Run`, `Outcome`, every `EventKind` (trigger, fields, JSON with its `type` tag), the `RunMachine` model (fed lines and time, drained by `take_outputs`, `Output::Event` and `Rebound`, `Clock`, generation-counter timers), every delay (500 ms settle, 350 ms combat capture, 1200 ms combat-end retry, the 4 s ranked rating wait, the hero wait), the Run lifecycle (`local-` ids, rebinding, end triggers and outcomes), options, selection, sells and rerolls, how a combat's result is decided, the `Tracker` service (four threads, the ordered save queue retrying 1 s to 30 s, live Snapshot polling, every `Notice`), `just tracker track`, and the whole-log replay tests.
- [history.db](history-db.md) — the SQLite file: WAL with a writer and a `query_only` reader, every table, column and index prefixed by where rows come from (`run_tracker_runs`, `run_tracker_events`, `run_tracker_tracked_items`, `run_tracker_hidden_items`, `imported_shop_odds`, `imported_item_odds`, `setting_pinned_items`, and the Build Advisor's `advisor_conversations`, `advisor_messages`, `imported_runs`, `imported_run_cards`, `imported_picks`, `imported_combats` and `imported_*_stats`), who writes what (the tracker owns the schema; the Advisor writes `advisor_*` and the Scraped run tables), migrations 1–9, the `user_version` rules (older backed up as `history.v<N>.bak.db` then migrated, newer refused), how saving an Event updates its Run's summary, rebinding a Run's id (rename or merge, Conversations moved with it), deletion by cascade (a Run's Conversations and their messages included), clearing, upload status codes, times in Unix ms, and example `sqlite3 -readonly` queries for inspecting it.
- [Database schema](db-schema.html) — the schema of `history.db` at version 9 on one page: the table prefixes (`advisor_` included) and who writes each table, the sixteen tables with every column, type, nullability and meaning (the tracker's seven, and the Build Advisor's Conversations, messages, Scraped runs and their statistics), an ER diagram, the whole schema folded into one SQL script, the indexes, the foreign keys to `run_tracker_runs(id)`, `advisor_conversations(id)` and `imported_runs(run_id)` and what cascades, the migrations and the backup made before them, the connections' pragmas, and `GameData.db` (read only, not ours).
- [Bazaar DB](bazaar-db.md) — reading bazaardb.gg in `crates/bazaardb` and the features built on it: the honest `GET` and how it tells a refusal from a Cloudflare challenge, why Turnstile needs a real browser view, `/api/shop-odds` and the built-in day 1–16 defaults, `/api/item-odds`, the `webview` feature (`script.js` capturing replies, the `#bazaar-tracker-find=<name>` search, the borderless popup moved by `WebView::place`); the Shop odds column beside the Economy and the Shop odds Widget (Refresh, Import JSON…), the odds button on a hovered item with its 20 s fallback, `accept`, the ITEM ODDS block at an encounter choice (`watched`, `choice_groups`, folding, ✕ to hide), the Tracked items pop-up, loading many items from Settings (random 0.5–4 s wait, 20 s skip), the debug panel, the history.db tables, and `just tracker shop-odds`.
- [Scrapers](scrapers.md) — how the Python scrapers in `apps/scraper/` read Bazaar DB: the two entry points (`scrape-odds`, `scrape-runs`) and what they share, the rules both keep (read only, a random wait between asks, carry on where stopped, atomic writes, a person passes Cloudflare's check), page data (the Next.js flight payload, plain HTTP) against `/api/*` (Turnstile, a browser), when the run scraper opens a browser and how it scrolls an `/api/run` list, parsing the flight payload (`T` rows, `$` references, finding props by shape), seasons from the site's script, and the run scraper in full: profiles and run feeds, every option, the `.bazaar-tracker/raw_data/scraper/builds/` files, and importing them for the Advisor with `just advisor import`.
