Advisor: หนึ่งคำถาม ตั้งแต่ส่งจนได้คำตอบ

12 พฤศจิกายน 2026 · branch feat/advisor-game-knowledge · อธิบายโค้ดที่มีอยู่ใน apps/advisor/ ตอนนี้ · รายละเอียดเต็มของ API และ tools อยู่ใน advisor.md · คำที่ขีดเส้นประ ชี้เพื่อดูความหมาย หรือคลิกเพื่อไปที่ Glossary

ภาพรวม

Advisor ไม่ได้ทำงานตาม turn ของเกม มันทำงานเมื่อผู้เล่นส่งคำถาม ทุกคำถามที่แอป gpui ส่งไปจะมี situation แนบไปด้วย คือสภาพเกม ณ ตอนนั้น: hero, Day, Hour, gold, Board, Stash, skills, Offer และ opponent ฝั่ง backend จะเอา situation นี้ไปทำสองอย่าง

  • แปลงเป็นข้อความวางไว้เหนือคำถาม ให้โมเดลอ่าน
  • เก็บไว้ใน state ของ run เพื่อให้ tools ใช้เป็นค่า default เช่น rate_options ที่ไม่ได้รับ argument จะใช้ Offer จาก situation

ส่วนที่ว่า Hour ใหม่ต่างจากเดิมอย่างไร เกิดจาก situation ที่เปลี่ยนไปเท่านั้น เมื่อ situation ต่างจากคำถามก่อน ๆ backend จะ mark คำถามเก่าว่าถามคนละสถานการณ์ และตัดผลจาก tool เก่าออก (ดู ถามต่อใน Hour ถัดไป)

โมเดลไม่เคยแตะ database เอง ตัวเลขทุกตัวมาจาก knowledge/ ผ่าน tools

หนึ่งคำถาม ตั้งแต่ต้นจนจบ

ผู้เล่นพิมพ์คำถามใน Conversation ของ Run หนึ่ง แอปส่งคำถามพร้อม situation ไปที่ backend แล้ว harness วน model call จนได้ reply ที่สมบูรณ์ ระหว่างนั้นทุกอย่างถูกส่งกลับมาทาง SSE

sequenceDiagram
  actor P as Player
  participant A as Advisor tab (gpui)
  participant API as messages router
  participant R as Runs.run_message
  participant H as tau_agent harness
  participant M as Model
  participant T as Tools
  participant DB as history.db
  P->>A: types a question (Enter)
  A->>A: build the situation (board read, Snapshot or Event)
  A->>API: POST text + situation + model
  API->>API: check text, situation schema and model, 409 if a reply runs
  API->>R: run_message
  R->>DB: load stored messages of the Conversation
  R->>R: model_history(stored, situation)
  R->>R: prepare: parse situation, tools_for(situation, sources)
  R->>H: build_harness(system, tools, history)
  R->>H: prompt_message(Situation for this question + Question)
  H->>DB: save the question as typed, with its situation
  loop each model call, at most 12
    H->>M: system + tools + messages
    M-->>H: thinking, text, tool calls (streamed)
    H-->>A: SSE delta, message_end, step
    H->>DB: save the assistant message and its step stats
    H->>T: run each tool call
    T-->>H: JSON result (numbers with n, seasons)
    H->>DB: save each tool result
  end
  R->>DB: save the reply's stats on its last message
  R-->>A: SSE stats, done

ทุก message ถูกบันทึกทันทีที่จบ (ผ่าน subscriber ของ harness) ถ้าผู้เล่นกด Stop สตรีมจะถูกปิด reply ถูกยกเลิก แต่ข้อความที่มาถึงแล้วยังถูกเก็บไว้ โดย mark stopReason: "aborted"

Input stack: โมเดลได้อะไรบ้าง

ทุกครั้งที่ harness เรียกโมเดล (หนึ่ง reply อาจเรียกหลายครั้ง) request จะประกอบด้วยชั้นต่อไปนี้ เรียงจากบนลงล่าง ชั้นบนนิ่งที่สุด ชั้นล่างเปลี่ยนบ่อยที่สุด การวางแบบนี้ทำให้ provider cache ส่วนต้นของ prompt ได้

คงที่ทุกคำถาม เปลี่ยนตามคำถามหรือ situation โตขึ้นระหว่าง reply
1
System prompt: กฎใน prompts/system.md ตามด้วยหัวข้อ ## Skills ที่มีรายการ skill หนึ่งบรรทัดต่อ skill
ไม่มี Board หรือ situation อยู่ในนี้ จึงเหมือนเดิมทุกคำถาม
2
Tool definitions: 10 ตัว แต่ละตัวมีชื่อ, description และ JSON schema ของ arguments
สร้างใหม่ทุก message ด้วย tools_for(situation, sources) แต่สิ่งที่ส่งให้โมเดลเหมือนเดิม เพราะ situation ถูกเก็บไว้ใน closure ของ tool
3
History: คำถาม, คำตอบ และผล tool ก่อนหน้าใน Conversation เดียวกัน เขียนใหม่ด้วย model_history
คำถามที่ถามคนละ situation จะถูก mark ว่าเก่า ผลจาก tool ที่อิง situation เก่าจะถูกตัดออก
4
คำถามนี้: ## Situation for this question (Board state ที่ render แล้ว) ตามด้วย ## Question และข้อความที่ผู้เล่นพิมพ์
สร้างด้วย question_message ส่วนที่บันทึกลง database คือข้อความตามที่พิมพ์ โดยเก็บ situation แยกไว้ข้าง ๆ
5
Reply นี้จนถึงตอนนี้: assistant message ที่มี tool calls และ tool result แต่ละตัว รวมถึงเนื้อหา skill เมื่อเรียก load_skill
เพิ่มขึ้นทุกรอบของ loop

1. System prompt

agents/advisor/agent.py สร้าง PROMPT ครั้งเดียวตอน import: เนื้อหาของ prompts/system.md แล้วต่อด้วยรายการ skill จาก catalog(SKILLS) กฎหลักที่อยู่ในนั้น ได้แก่

  • อ่าน situation เหนือคำถามก่อนตอบ และห้ามขอให้ผู้เล่นพิมพ์สิ่งที่ situation แสดงอยู่แล้ว
  • ตอบจาก situation ของคำถามล่าสุดเท่านั้น ถ้าต้องใช้ผลจาก tool ให้เรียกใหม่ ห้ามใช้ผลจากคำถามก่อน
  • ทุกตัวเลขต้องมาจาก tool และต้องบอก n ทุกครั้ง ถ้าข้อมูลน้อยกว่า 10 runs ต้องบอกว่าข้อมูลบาง
  • บอกลำดับการใช้ tool ตามชนิดคำถาม: จัดอันดับ Offer ใช้ rate_options แล้ว synergy แล้ว suggest, Offer ที่เป็น encounter ใช้ shop_plan แล้ว suggest, จัด Board ใช้ arrangement และหา build ที่คล้ายกันใช้ similar_runs
  • ตอบสั้น: นำด้วยการตัดสินใจ, ตามด้วยเหตุผล 1–2 ประโยค แล้วบอกความมั่นใจ จากนั้นจบด้วย follow_ups

2. Tools และ skills

Toolอ่าน situation?ทำอะไร
find_cardใช่ค้นการ์ดใน GameData.db: tier, size, text, tags
rate_optionsใช่ (default คือ Offer)จำนวนครั้งที่ถูกเสนอและถูกเลือก, ความเข้ากับ Board, พร้อม n
synergyใช่การ์ดที่มักอยู่ด้วยกันบน Board สุดท้ายของ Scraped runs: lift, runs together
suggestใช่รับอันดับและเหตุผลจากโมเดล แล้วเติมตัวเลขและ source runs เพื่อวาดเป็นการ์ดแนะนำ
shop_planใช่ (default คือ Day)Shop odds, item odds ของการ์ดที่ต้องการ และ encounter ที่ run เก่ง ๆ เลือก
arrangementใช่ (default คือ Board)คู่การ์ดที่อยู่ติดกัน, ตำแหน่งที่ใช้บ่อย และ text ที่พูดถึงตำแหน่ง
similar_runsใช่ (default คือ Board)Scraped runs ที่ Board สุดท้ายคล้ายกับของผู้เล่น
follow_upsไม่คำถามถัดไป 2–3 ข้อ ถ้าเรียกหลังจากมีคำตอบแล้ว reply จะจบ
ask_userไม่ถามผู้เล่นพร้อมตัวเลือก และจบ reply ทันที
load_skillไม่คืนเนื้อหาของ skills/<name>/SKILL.md (ตอนนี้มีแค่ combat)

Skills ไม่ได้อยู่ใน prompt ตั้งแต่แรก system prompt มีแค่ชื่อและคำอธิบายหนึ่งบรรทัด ถ้าโมเดลต้องการเนื้อหา มันต้องเรียก load_skill เนื้อหาจะเข้ามาในชั้นที่ 5 ในรูป tool result วิธีนี้ทำให้ prompt สั้น และความรู้เรื่องเกมถูกอ่านเฉพาะเมื่อคำถามต้องใช้

3. History

Runs.run_message โหลด message ที่เก็บไว้ทั้งหมดของ Conversation (แต่ละอันมี situation ของคำถามที่มันตอบ) แล้วส่งให้ model_history(stored, situation) ซึ่งเทียบ situation แต่ละตัวกับ situation ตอนนี้แบบ JSON ทั้งก้อน

flowchart TD
  m["each stored message"] --> kind{"what is it?"}
  kind -->|"user question"| same1{"its situation = now?"}
  same1 -->|"yes"| keep1["sent as stored"]
  same1 -->|"no"| mark["prefixed: Asked on Day 4, Hour 1 in Shop, with a different situation from now"]
  kind -->|"tool result"| st{"tool reads the situation? rate_options, synergy, suggest, shop_plan, arrangement, similar_runs"}
  st -->|"no: find_card, follow_ups, ask_user, load_skill"| keep2["sent as stored"]
  st -->|"yes"| same2{"its question's situation = now?"}
  same2 -->|"yes"| keep3["sent as stored: no need to call again"]
  same2 -->|"no"| drop["replaced: this result was for an earlier situation, call it again"]
  kind -->|"assistant"| keep4["sent as stored"]

การแก้นี้มีผลกับสิ่งที่ส่งให้โมเดลเท่านั้น message ใน database ไม่ถูกแก้ ส่วน tool call ยังอยู่ครบ ทุก call จึงยังมี result คู่กัน

4. Situation และคำถาม

แอปสร้าง situation จากแหล่งที่ดีที่สุดที่มี (รายละเอียดใน gpui-app.md)

กรณีSituation มาจากมี Offer / opponent?
Live run ที่อ่าน board ได้แล้วboard read ล่าสุดมี
Run อื่น หรือ Live run ที่ยังไม่มี readSnapshot สุดท้ายของ Runไม่มี
แนบ Event มาด้วยSnapshot ณ Event นั้น โดย Options เป็น Offer และมี field eventมี Offer

Backend ตรวจ situation ด้วย Pydantic (situation.py, extra="forbid") ถ้าไม่ผ่าน route จะตอบ 400 และระบุ field ที่ผิด จากนั้น render_situation จะแปลงเป็นข้อความตามลำดับนี้: event (ถ้ามี) → Hero · Day/Hour · game_state → Gold · Level · Health → Board พร้อมจำนวนช่องที่ใช้ → slot effects → Stash → Skills → Offer → Opponent

Field ที่ไม่ได้ส่งมาจะเขียนว่า not sent. และ list ว่างจะเขียนว่า empty. ทำให้โมเดลแยกได้ระหว่างข้อมูลที่ไม่รู้กับข้อมูลที่ไม่มีจริง

5. สิ่งที่เกิดใน reply นี้

หลังจากโมเดลตอบด้วย tool calls, harness จะรัน tools แล้วต่อ assistant message กับ tool results ท้าย messages ก่อนเรียกโมเดลรอบใหม่ Tool บางตัวใช้ model_view ส่งให้โมเดลเห็นแค่บางส่วน เช่น suggest ให้โมเดลเห็นแค่อันดับและตัวเลข ส่วน source runs (Board, skills, ลิงก์) ส่งให้แอปไปวาดการ์ดเท่านั้น

ตัวอย่าง: ข้อความที่โมเดลเห็นจริง

Run ของ Jules, Day 5 Hour 2 ในร้านค้า บน Board มี Giant Lollipop (Large) และ Pizza Cutter (Small) ข้อความชั้นที่ 4 จะออกมาแบบนี้

Hero: Jules · Day 5, Hour 2 · Shop
Gold 14 · Level 6 · Health 900/900

Board (4 of 10 slots used, 6 free):
- slot 1: Giant Lollipop (Large, Silver)
- slot 4: Pizza Cutter (Small, Bronze)

Skills: empty.

- Decanter (merchant item, Small, Bronze)

## Question

ควรเลือกตัวไหนดี

ตัวอย่างนี้ตัด id ออกเพื่อให้อ่านง่าย ของจริงการ์ดที่แอปรู้ id จะมี [id …] ต่อท้าย

request ทั้งก้อนที่ส่งไป provider แบบ OpenAI-compatible มีรูปร่างประมาณนี้

{
  "model": "ADVISOR_MODEL or the picked model",
  "messages": [
    { "role": "system", "content": "You are the Advisor for The Bazaar … ## Skills\n- combat: …" },
    { "role": "user", "content": "[Asked on Day 4, Hour 1 in Shop, with a different situation from now.]\n\nWhich shop?" },
    { "role": "assistant", "tool_calls": [{ "function": { "name": "shop_plan", "arguments": "{…}" } }] },
    { "role": "tool", "content": "[This shop_plan result was for an earlier situation … Call shop_plan again …]" },
    { "role": "assistant", "content": "Go to …" },
    { "role": "user", "content": "## Situation for this question\n\nHero: Jules · Day 5, Hour 2 · Shop\n…\n\n## Question\n\nควรเลือกตัวไหนดี" }
  ],
  "tools": [ { "type": "function", "function": { "name": "rate_options", "parameters": { … } } }, "… 10 in all" ],
  "stream": true
}

Tool loop: คิดกี่รอบ และหยุดเมื่อไร

flowchart TD
  start["prompt_message(question)"] --> modelcall["model call: system + tools + messages"]
  modelcall --> out{"what came back?"}
  out -->|"text only, no tool calls"| stop1["reply ends"]
  out -->|"tool calls"| run["run the tools, append results"]
  run --> ask{"ask_user succeeded?"}
  ask -->|"yes"| stop2["reply ends: waits for the player's answer as the next message"]
  ask -->|"no"| fu{"follow_ups succeeded and the reply already has text?"}
  fu -->|"yes"| stop3["reply ends"]
  fu -->|"no"| turns{"12 model calls reached?"}
  turns -->|"yes"| stop4["reply ends: MAX_TURNS"]
  turns -->|"no"| modelcall

ลำดับปกติของคำถามประเภท "เลือกตัวไหนดี" มีสามรอบ

  1. รอบ 1 โมเดลเรียก rate_options กับ synergy (อาจเรียกพร้อมกันในรอบเดียว)
  2. รอบ 2 โมเดลอ่านตัวเลข แล้วเรียก suggest พร้อมอันดับและเหตุผล
  3. รอบ 3 โมเดลเขียนคำตอบ แล้วเรียก follow_ups ซึ่งทำให้ reply จบ
tau_agent ไม่อ่าน flag terminate ของ tool เอง ตัวที่หยุด loop คือ runner ใน backend/agent/runner.py ซึ่งเรียก ends_reply() หลังทุก TurnEndEvent แล้ว break ออกก่อนเรียกโมเดลรอบถัดไป

Output

SSE events ที่แอปได้

Eventเมื่อไรมีอะไร
message_start / message_endต้นและท้ายของ message (คำถาม, assistant, tool result)message ทั้งก้อน โดยคำถามจะเป็นข้อความตามที่พิมพ์ ไม่มี situation ที่ render แล้ว
deltaระหว่างที่ assistant กำลังสตรีมkind เป็น text, thinking หรือ toolcall, พร้อม index และ delta
stepหลัง message_end ของ assistant แต่ละอันstats ของ model call นั้น และ seq ใน database
statsเมื่อ reply จบstats รวมทั้ง reply: model, เวลา, tokens, cost, จำนวน tool calls
errorเมื่อ reply ล้มเหลวข้อความ error
doneท้ายสุดเสมอไม่มี

สิ่งที่บันทึกลง history.db

แต่ละ message เป็นหนึ่งแถวใน advisor_messages เรียงตาม seq

  • คำถาม เก็บข้อความตามที่ผู้เล่นพิมพ์ พร้อม situation ที่ส่งมาด้วย แอปใช้ situation นี้แสดงแถว Context และ backend ใช้ mark คำถามนี้ในรอบต่อ ๆ ไป
  • Assistant message แต่ละอัน (thinking, text, tool calls) เก็บพร้อม stats ของ step นั้น
  • Tool result แต่ละอัน
  • Stats ของทั้ง reply เก็บไว้บน assistant message สุดท้าย

สิ่งที่แอปแสดง

flowchart LR

  • ถ้าผู้เล่นถามต่อโดย situation ไม่เปลี่ยน (เช่น "แล้ววางตรงไหน" ใน Hour เดิมโดยยังไม่ได้ซื้อ) ผลจาก tool เดิมจะยังถูกส่งไป โมเดลจึงไม่ต้องเรียก tool ซ้ำ
  • situation ที่ต่างกันแม้แต่ field เดียว (เช่น gold) จะถือว่าเป็นคนละ situation เพราะเทียบเป็น JSON ทั้งก้อน

สิ่งที่ Advisor ยังไม่ทำ

  • ไม่ถูกปลุกเองตาม stage ไม่มี decision point แบบ "เพิ่งเปิด Offer" Advisor ทำงานเมื่อผู้เล่นถามเท่านั้น (หรือเมื่อกดปุ่ม ✨ What should I do? ซึ่งก็คือการส่งคำถามสำเร็จรูป)
  • game_state เป็น string อิสระ ถูก render ลง prompt แต่ไม่มีโค้ดตัวไหนแยกทางตามค่านี้ และชุด tools เหมือนกันทุก stage
  • การแยกตาม stage ที่มีอยู่ มีแค่ kind ของการ์ดใน Offer (encounter_choice ไปทาง shop_plan, item ไปทาง rate_options) และกฎใน system prompt
  • ไม่มี memory ข้าม Run แต่ละ Conversation ผูกกับ Run เดียว

Glossary

การ์ดขอบบนสีน้ำเงินเป็นคำจาก GLOSSARY.md ของ repo ส่วนการ์ดขอบบนสีม่วงเป็นคำที่ใช้ในเอกสารนี้

คำของโดเมน (GLOSSARY.md)

Run
การเล่น The Bazaar หนึ่งรอบ ตั้งแต่เลือก hero จนชนะหรือแพ้
Live run
Run ที่กำลังเล่นอยู่ตอนนี้ และ tracker กำลังติดตามอยู่
Event
สิ่งหนึ่งที่เกิดขึ้นใน Run และถูกบันทึกไว้ เช่น มีตัวเลือกเสนอมา, เลือกไอเทม, combat เริ่มหรือจบ
Snapshot
Board, Stash, skills และค่าสถานะของผู้เล่น ณ ขณะหนึ่งของ Run บันทึกไว้คู่กับ Event
Board
ไอเทมที่ผู้เล่นใช้งานอยู่ วางบน 10 ช่อง: Small ใช้ 1 ช่อง, Medium 2 ช่อง และ Large 3 ช่อง
Stash
ไอเทมที่ผู้เล่นถือไว้ แต่ไม่ได้วางบน Board
Offer
การ์ดที่เกมเสนอให้ผู้เล่น ณ ขณะหนึ่ง ให้ซื้อ รับ หรือเลือก ได้แก่ไอเทมของ merchant, loot หรือตัวเลือกของ encounter
Scraped run
Run ของผู้เล่นคนใดก็ได้ ที่ run scraper บันทึกมาจาก Bazaar DB พร้อม Board สุดท้าย, skills และ timeline Advisor ใช้นับสถิติ แต่ไม่แสดงในรายการ runs
Advisor
agent ที่ผู้เล่นถามเรื่อง build ได้: เลือกไอเทมไหน, อะไรเข้ากัน, ไปร้านไหน, จัด Board อย่างไร, เลือก skill ไหน ตอบจาก card catalog, odds และ Scraped runs
Conversation
ข้อความชุดหนึ่งระหว่างผู้เล่นกับ Advisor เกี่ยวกับ Run เดียว Run หนึ่งมีได้หลาย Conversation

คำในเอกสารนี้

Situation
JSON ที่แอปส่งไปกับทุกคำถาม บอกสภาพเกม ณ ตอนนั้น: hero, Day, Hour, gold, Board, Stash, skills, Offer และ opponent ละ field ได้ทุกตัว แต่ field ที่ส่งมาต้องถูกชนิด และ key ที่ไม่รู้จักจะถูกปฏิเสธ
Day / Hour
ตำแหน่งในเวลาของ Run แอปแสดงเป็น D5 H2 Advisor ไม่ถูกเรียกเมื่อ Hour เปลี่ยน มันเห็น Hour เป็นแค่ field หนึ่งใน Situation
Reply
ทุกอย่างที่ Advisor ทำเพื่อตอบคำถามหนึ่งข้อ: model call หลายครั้ง, tool calls และคำตอบ จบด้วย follow_ups, ask_user, ข้อความที่ไม่เรียก tool หรือครบ 12 model calls
Model call step
การส่ง request ไปโมเดลหนึ่งครั้ง หนึ่ง Reply มีได้สูงสุด 12 ครั้ง แต่ละครั้งได้ stats ของตัวเองใน event step
Harness
ตัววน loop ของ tau_agent ถือ system prompt, tools และ messages ไว้ เรียกโมเดล รัน tools และส่ง event ออกมา build_harness สร้างใหม่ทุกคำถาม
System prompt
กฎของ Advisor กับรายการ skill หนึ่งบรรทัดต่อ skill ไม่มี Situation อยู่ในนี้ จึงเหมือนเดิมทุกคำถามและ provider cache ได้
Tool
function ที่โมเดลเรียกได้ รับ arguments ตาม JSON schema และคืน JSON ตัวเลขทุกตัวในคำตอบต้องมาจาก tool ที่อ่าน knowledge/
Skill
ความรู้เรื่องเกมในไฟล์ skills/<name>/SKILL.md prompt มีแค่ชื่อกับคำอธิบาย เนื้อหาจะเข้ามาเมื่อโมเดลเรียก load_skill
n
จำนวน run ที่ตัวเลขหนึ่ง ๆ คำนวณมา (sample size) ต้องบอกคู่กับตัวเลขเสมอ ถ้าต่ำกว่า 10 ถือว่าข้อมูลบาง
SSE
Server-Sent Events: คำตอบของ POST เป็น stream ของ event ทีละก้อน (event: ชื่อ, data: JSON) แอปอ่านบน thread ของตัวเองด้วย ureq
Decision point
จังหวะที่เกมปลุก agent ให้ตัดสินใจเอง เช่น เพิ่งเจอศพหรือทำงานเสร็จ เป็นคำจาก among-us-ai ซึ่ง Advisor ยังไม่มี
