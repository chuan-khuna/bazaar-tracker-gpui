Overview

The gpui app keeps one database of its own: history.db, a SQLite file in the data folder (.bazaar-tracker\history.db for a debug build, %APPDATA%\BazaarTracker\history.db for a release one; see data-folder.md). It holds seven tables:

TableHoldsKeyAdded
runsOne summary row for each Runid1
eventsEvery Event of every Run, details as JSONseq (and unique id)1, 2
shop_oddsBazaar DB's Shop odds, one row for each dayday3
item_oddsBazaar DB's odds for one item, per hero and owned tier(template_id, hero, tier)4
tracked_itemsItems tracked in a Run(run_id, template_id)5
hidden_itemsItems hidden from a Run's odds(run_id, template_id)6
pinned_itemsItems pinned for a hero, tracked in all that hero's Runs(hero, template_id)7

The schema is our own, not the original tracker's. The terms (Run, Event, Snapshot, Shop odds) are defined in GLOSSARY.md. How the code reads and writes these tables is in history-db.md; this page is the schema alone.

Conventions. Every time is an INTEGER of milliseconds since the Unix epoch, in a column ending _ms. Template ids are lower-cased before they are saved. Booleans are INTEGER 0 or 1. JSON is stored as TEXT.

The file and its connections

History::open (history/mod.rs) creates the file if it is missing, migrates it, and keeps two connections, each behind a Mutex:

ConnectionPragmasUsed for
writerforeign_keys = ON, busy timeout 5 s, journal_mode = WAL; runs the migrationsEvery write
readerforeign_keys = ON, busy timeout 5 s, query_only = trueEvery read

WAL mode lets the window list Runs while the tracker is saving an Event. The schema version is PRAGMA user_version.

Only runs has foreign keys pointing at it. pinned_items, item_odds and shop_odds stand alone: they match a Run by hero or template id in code, not by a key, so deleting a Run never touches them.

The whole schema as SQL

What a file at version 7 holds, with the seven migrations folded into one script. It is for reading; the app builds the file from MIGRATIONS, never from this.

PRAGMA user_version = 7;

CREATE TABLE runs (
    id          TEXT PRIMARY KEY,           -- the game's run id, or 'local-…' until it is known
    started_ms  INTEGER NOT NULL,
    ended_ms    INTEGER,                    -- NULL while not ended
    ended       INTEGER NOT NULL DEFAULT 0, -- 1 once ended
    hero        TEXT,
    day         INTEGER,                    -- the furthest day reached
    victories   INTEGER,
    losses      INTEGER,
    outcome     TEXT                        -- 'Win', 'Loss', 'Unknown'; NULL while not ended
);
CREATE INDEX runs_by_start ON runs (started_ms);

CREATE TABLE events (
    seq           INTEGER PRIMARY KEY AUTOINCREMENT,
    id            TEXT NOT NULL UNIQUE,
    run_id        TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    kind          TEXT NOT NULL,            -- the EventKind's `type` tag
    timestamp_ms  INTEGER NOT NULL,
    day           INTEGER,
    hour          INTEGER,
    details       TEXT NOT NULL,            -- the EventKind as JSON
    upload_status INTEGER NOT NULL DEFAULT 0 -- 0 waiting, 1 sent, 3 rejected
);
CREATE INDEX events_by_run ON events (run_id, timestamp_ms, seq);
CREATE INDEX events_waiting_for_upload ON events (seq) WHERE upload_status = 0;

CREATE TABLE shop_odds (
    day        INTEGER PRIMARY KEY,
    samples    INTEGER NOT NULL,
    bronze     REAL NOT NULL,
    silver     REAL NOT NULL,
    gold       REAL NOT NULL,
    diamond    REAL NOT NULL,
    saved_ms   INTEGER NOT NULL
);

CREATE TABLE item_odds (
    template_id TEXT NOT NULL,
    hero        TEXT NOT NULL,
    tier        TEXT NOT NULL,              -- the owned tier, or 'None' when not owned
    url_id      TEXT NOT NULL,
    item_name   TEXT NOT NULL,
    body        TEXT NOT NULL,              -- Bazaar DB's answer, as it came
    saved_ms    INTEGER NOT NULL,
    PRIMARY KEY (template_id, hero, tier)
);

CREATE TABLE tracked_items (
    run_id      TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    added_ms    INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

CREATE TABLE hidden_items (
    run_id      TEXT NOT NULL REFERENCES runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    hidden_ms   INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

CREATE TABLE pinned_items (
    hero        TEXT NOT NULL,
    template_id TEXT NOT NULL,
    pinned_ms   INTEGER NOT NULL,
    PRIMARY KEY (hero, template_id)
);

Tables

runs

One row for each Run: the summary the sidebar lists. The row is created by the Run's first saved Event and updated as each new Event is saved (see Saving an Event).

ColumnTypeNullHolds
idTEXTPKThe game's run id, or a local- id until it is known (then rebound)
started_msINTEGERnot nullWhen the Run started; the first Event's time, then RunStarted's
ended_msINTEGERnullWhen it ended; NULL while it has not
endedINTEGERnot null, default 01 once ended
heroTEXTnullThe hero, as the game names it
dayINTEGERnullThe furthest day reached; only grows
victoriesINTEGERnullWins so far, or at the end
lossesINTEGERnullLosses so far, or at the end
outcomeTEXTnullWin, Loss or Unknown; NULL while not ended

events

One row for each Event. Saving an Event whose id is already there changes nothing, so a retried save cannot double up.

ColumnTypeNullHolds
seqINTEGERPK, autoincrementInsertion order; breaks ties between equal times
idTEXTnot null, uniqueThe Event's id
run_idTEXTnot null, FKruns(id), cascading on delete and update
kindTEXTnot nullRunStarted, OptionsPresented, Selected, Sold, Rerolled, CombatStart, CombatEnd or RunEnded
timestamp_msINTEGERnot nullWhen the Event was made
dayINTEGERnullThe game's day
hourINTEGERnullThe game's hour
detailsTEXTnot nullThe EventKind as JSON, type tag included; the id, Run, time, day and hour live in columns, not in here. Fields per kind: run-state-machine.md
upload_statusINTEGERnot null, default 00 waiting, 1 sent, 3 rejected (an unknown code reads as waiting). Upload is never started by the app; see upload.md

shop_odds

Bazaar DB's Shop odds: the chance of each tier in a shop, one row for each day. Saving replaces every row at once. A new file is seeded with the built-in day 1–16 defaults so the odds work offline.

ColumnTypeNullHolds
dayINTEGERPKThe day
samplesINTEGERnot nullHow many shops the odds come from
bronze, silver, gold, diamondREALnot nullThe chance of each tier
saved_msINTEGERnot nullWhen they were saved

item_odds

Bazaar DB's odds for one item, for one hero and the tier the player owns it at. Saving replaces the row with the same key, so the same item for another hero or tier is kept. Only odds the player asked for (or imported) are saved.

ColumnTypeNullHolds
template_idTEXTPKThe card's template id, lower-cased
heroTEXTPKThe hero the odds are for
tierTEXTPKThe owned tier, or None (NOT_OWNED in src/tracking/item_odds.rs) when not owned
url_idTEXTnot nullThe item's Bazaar DB id, so a refresh can name it
item_nameTEXTnot nullThe item's name
bodyTEXTnot nullBazaar DB's JSON answer as it came; read with bazaardb::item_odds::parse_json
saved_msINTEGERnot nullWhen they were saved

tracked_items

The items the player tracks in a Run, to see their odds beside each merchant. Adding twice changes nothing.

ColumnTypeNullHolds
run_idTEXTPK, FKruns(id), cascading on delete and update
template_idTEXTPKThe card's template id, lower-cased
added_msINTEGERnot nullWhen it was tracked; the list is read in this order

hidden_items

The items the player hid from the odds beside each merchant in a Run. Same shape as tracked_items.

ColumnTypeNullHolds
run_idTEXTPK, FKruns(id), cascading on delete and update
template_idTEXTPKThe card's template id, lower-cased
hidden_msINTEGERnot nullWhen it was hidden

pinned_items

The items the player pins for a hero. The app tracks them in every Run of that hero, on top of the Run's own tracked_items. They belong to the hero, not a Run, so deleting or rebinding a Run leaves them.

ColumnTypeNullHolds
heroTEXTPKThe hero as the game names it, such as Jules
template_idTEXTPKThe card's template id, lower-cased
pinned_msINTEGERnot nullWhen it was pinned

Foreign keys and cascades

Foreign keys are on for both connections. Three tables point at runs(id), all with ON DELETE CASCADE ON UPDATE CASCADE:

flowchart LR
  runs[("runs.id")]
  events["events.run_id"]
  tracked["tracked_items.run_id"]
  hidden["hidden_items.run_id"]
  events -->|"cascade"| runs
  tracked -->|"cascade"| runs
  hidden -->|"cascade"| runs
  pinned["pinned_items"]
  item["item_odds"]
  shop["shop_odds"]
  pinned -.->|"by hero, in code"| runs
  • Deleting a Run removes its Events, tracked items and hidden items. The odds tables and pinned_items are untouched.
  • Rebinding a Run from a local- id to the game's id is an UPDATE runs SET id, and the three child tables follow. When a Run with the new id already exists, the two are merged in code instead (Rebinding a Run's id).

Migrations

MIGRATIONS is a list of SQL batches. Migration N takes a file from user_version N−1 to N, in one transaction with the version bump. An older file runs only the ones it lacks; a file newer than the app is refused with Error::NewerSchema. New migrations go at the end, and one that has shipped is never changed.

#Adds
1runs, events, events_by_run, runs_by_start
2events.upload_status (default 0) and the partial index events_waiting_for_upload
3shop_odds
4item_odds
5tracked_items
6hidden_items
7pinned_items

GameData.db (read only)

The app also reads the game's own GameData.db to name cards, but never writes it and does not own its schema. CardCatalog copies the file first and opens the copy with SQLITE_OPEN_READ_ONLY, reading the cards table (Id, Data). See card-catalog-and-art.md.

Inspecting the file

Open it read-only while the app or just app track is running, so nothing typed can write to it:

-- sqlite3 -readonly .bazaar-tracker\history.db
PRAGMA user_version;          -- 7
.schema
SELECT name, type FROM sqlite_master WHERE name NOT LIKE 'sqlite_%' ORDER BY type, name;
PRAGMA foreign_key_check;     -- should return nothing

More queries are in history-db.md.
