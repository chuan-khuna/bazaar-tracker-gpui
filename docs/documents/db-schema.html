Overview

The gpui app keeps one database of its own: history.db, a SQLite file in the data folder (.bazaar-tracker\history.db for a debug build, %APPDATA%\BazaarTracker\history.db for a release one; see data-folder.md). Each table's prefix says where its rows come from (2026-11-08.002):

PrefixRows come fromIf lost
run_tracker_Player.log and memory reads, as you play; and what the player tracks or hides in a RunGone for good: the only copy
imported_Bazaar DB, the scrapers' files, built-in defaultsFetched or imported again
setting_The player's own choices that outlive a RunChosen again by hand
advisor_The Build Advisor: the player's Conversations about a Run and the repliesGone for good: the only copy

The tracker app owns the schema and is the only one that migrates the file (ADR 0002). The Build Advisor writes the advisor_ tables and the Scraped run tables (imported_runs, its three row tables and the three _stats tables); the tracker writes the rest. It holds sixteen tables:

The schema is our own, not the original tracker's. The terms (Run, Event, Snapshot, Shop odds) are defined in GLOSSARY.md. How the code reads and writes these tables is in history-db.md; this page is the schema alone.

Conventions. Every time is an INTEGER of milliseconds since the Unix epoch, in a column ending _ms. Template ids are lower-cased before they are saved. Booleans are INTEGER 0 or 1. JSON is stored as TEXT.

The file and its connections

History::open (history/mod.rs) creates the file if it is missing, migrates it, and keeps two connections, each behind a Mutex:

ConnectionPragmasUsed for
writerforeign_keys = ON, busy timeout 5 s, journal_mode = WAL; runs the migrationsEvery write
readerforeign_keys = ON, busy timeout 5 s, query_only = trueEvery read

WAL mode lets the window list Runs while the tracker is saving an Event. The schema version is PRAGMA user_version.

Keys point at run_tracker_runs (from its three child tables and from advisor_conversations), at advisor_conversations (from advisor_messages) and at imported_runs (from its three row tables). setting_pinned_items, the odds and the _stats tables stand alone: they match by hero, season or card id in code, not by a key, so deleting a Run never touches them.

The whole schema as SQL

What a file at version 9 holds, with the nine migrations folded into one script. It is for reading; the app builds the file from MIGRATIONS, never from this. (Columns added by ALTER TABLE sit last in a migrated file, so .schema shows source after imported_ms.)

PRAGMA user_version = 9;

-- run_tracker_: what the tracker records while you play.
CREATE TABLE run_tracker_runs (
    id          TEXT PRIMARY KEY,           -- the game's run id, or 'local-…' until it is known
    started_ms  INTEGER NOT NULL,
    ended_ms    INTEGER,                    -- NULL while not ended
    ended       INTEGER NOT NULL DEFAULT 0, -- 1 once ended
    hero        TEXT,
    day         INTEGER,                    -- the furthest day reached
    victories   INTEGER,
    losses      INTEGER,
    outcome     TEXT                        -- 'Win', 'Loss', 'Unknown'; NULL while not ended
);
CREATE INDEX run_tracker_runs_by_start ON run_tracker_runs (started_ms);

CREATE TABLE run_tracker_events (
    seq           INTEGER PRIMARY KEY AUTOINCREMENT,
    id            TEXT NOT NULL UNIQUE,
    run_id        TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    kind          TEXT NOT NULL,            -- the EventKind's `type` tag
    timestamp_ms  INTEGER NOT NULL,
    day           INTEGER,
    hour          INTEGER,
    details       TEXT NOT NULL,            -- the EventKind as JSON
    upload_status INTEGER NOT NULL DEFAULT 0 -- 0 waiting, 1 sent, 3 rejected
);
CREATE INDEX run_tracker_events_by_run ON run_tracker_events (run_id, timestamp_ms, seq);
CREATE INDEX run_tracker_events_waiting_for_upload ON run_tracker_events (seq) WHERE upload_status = 0;

CREATE TABLE run_tracker_tracked_items (
    run_id      TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    added_ms    INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

CREATE TABLE run_tracker_hidden_items (
    run_id      TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    hidden_ms   INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

-- imported_: data brought in from outside.
CREATE TABLE imported_shop_odds (
    day         INTEGER PRIMARY KEY,
    samples     INTEGER NOT NULL,
    bronze      REAL NOT NULL,
    silver      REAL NOT NULL,
    gold        REAL NOT NULL,
    diamond     REAL NOT NULL,
    imported_ms INTEGER NOT NULL,
    source      TEXT NOT NULL DEFAULT 'bazaardb' -- 'bazaardb' or 'builtin'
);

CREATE TABLE imported_item_odds (
    template_id TEXT NOT NULL,
    hero        TEXT NOT NULL,
    tier        TEXT NOT NULL,              -- the owned tier, or 'None' when not owned
    url_id      TEXT NOT NULL,
    item_name   TEXT NOT NULL,
    body        TEXT NOT NULL,              -- Bazaar DB's answer, as it came
    imported_ms INTEGER NOT NULL,
    source      TEXT NOT NULL DEFAULT 'bazaardb', -- 'bazaardb' or 'scraper'
    PRIMARY KEY (template_id, hero, tier)
);

-- setting_: the player's own choices.
CREATE TABLE setting_pinned_items (
    hero        TEXT NOT NULL,
    template_id TEXT NOT NULL,
    pinned_ms   INTEGER NOT NULL,
    PRIMARY KEY (hero, template_id)
);

-- advisor_: the Build Advisor's Conversations, written by the Advisor.
CREATE TABLE advisor_conversations (
    id          TEXT PRIMARY KEY,
    run_id      TEXT NOT NULL REFERENCES run_tracker_runs(id) ON UPDATE CASCADE ON DELETE CASCADE,
    title       TEXT NOT NULL,
    day         INTEGER,                    -- the game's day and hour when it was started
    hour        INTEGER,
    created_ms  INTEGER NOT NULL
);
CREATE INDEX advisor_conversations_by_run ON advisor_conversations (run_id, created_ms);

CREATE TABLE advisor_messages (
    conversation_id TEXT NOT NULL REFERENCES advisor_conversations(id) ON UPDATE CASCADE ON DELETE CASCADE,
    seq             INTEGER NOT NULL,       -- order within the Conversation
    role            TEXT NOT NULL,
    message         TEXT NOT NULL,          -- tau_agent's message as JSON
    stats           TEXT,                   -- the reply's stats as JSON
    created_ms      INTEGER NOT NULL,
    PRIMARY KEY (conversation_id, seq)
);

-- imported_: Scraped runs and what the importer works out from them, written by the Advisor.
CREATE TABLE imported_runs (
    run_id       TEXT PRIMARY KEY,
    profile_id   TEXT,
    hero         TEXT NOT NULL,
    season       INTEGER,
    created_at   TEXT,                      -- the site's time, as given
    wins         INTEGER,
    losses       INTEGER,
    victory_tier TEXT,
    url          TEXT
);
CREATE INDEX imported_runs_by_hero ON imported_runs (hero, season);

CREATE TABLE imported_run_cards (
    run_id      TEXT NOT NULL REFERENCES imported_runs(run_id) ON UPDATE CASCADE ON DELETE CASCADE,
    card_id     TEXT NOT NULL,              -- a GameData.db id
    kind        TEXT NOT NULL,              -- 'board' or 'skill'
    tier        TEXT,
    slot        INTEGER,
    size        INTEGER,
    enchantment TEXT
);
CREATE INDEX imported_run_cards_by_run ON imported_run_cards (run_id);

CREATE TABLE imported_picks (
    run_id      TEXT NOT NULL REFERENCES imported_runs(run_id) ON UPDATE CASCADE ON DELETE CASCADE,
    day         INTEGER,
    hour        INTEGER,
    card_id     TEXT NOT NULL,
    tier        TEXT,
    taken       INTEGER NOT NULL            -- 1 taken, 0 passed over
);
CREATE INDEX imported_picks_by_run ON imported_picks (run_id, day, hour);

CREATE TABLE imported_combats (
    run_id      TEXT NOT NULL REFERENCES imported_runs(run_id) ON UPDATE CASCADE ON DELETE CASCADE,
    day         INTEGER,
    hour        INTEGER,
    outcome     TEXT
);
CREATE INDEX imported_combats_by_run ON imported_combats (run_id, day, hour);

-- imported_pick_stats and imported_adjacency_stats have the same columns and key.
CREATE TABLE imported_pair_stats (
    hero        TEXT NOT NULL,
    season      INTEGER NOT NULL,
    a           TEXT NOT NULL,
    b           TEXT NOT NULL,
    n           INTEGER NOT NULL,           -- how many Scraped runs the numbers come from
    lift        REAL,
    win_gain    REAL,
    PRIMARY KEY (hero, season, a, b)
);

Foreign keys and cascades

Foreign keys are on for both connections. Four tables point at run_tracker_runs(id), advisor_messages points at advisor_conversations(id), and three point at imported_runs(run_id), all with ON DELETE CASCADE ON UPDATE CASCADE:

flowchart LR
  runs[("run_tracker_runs.id")]
  events["run_tracker_events.run_id"]
  tracked["run_tracker_tracked_items.run_id"]
  hidden["run_tracker_hidden_items.run_id"]
  conversations["advisor_conversations.run_id"]
  messages["advisor_messages.conversation_id"]
  events -->|"cascade"| runs
  tracked -->|"cascade"| runs
  hidden -->|"cascade"| runs
  conversations -->|"cascade"| runs
  messages -->|"cascade"| conversations
  scraped[("imported_runs.run_id")]
  cards["imported_run_cards.run_id"]
  picks["imported_picks.run_id"]
  combats["imported_combats.run_id"]
  cards -->|"cascade"| scraped
  picks -->|"cascade"| scraped
  combats -->|"cascade"| scraped
  pinned["setting_pinned_items"]
  item["imported_item_odds"]
  shop["imported_shop_odds"]
  pinned -.->|"by hero, in code"| runs
  • Deleting a Run removes its Events, tracked items, hidden items and Conversations, and each Conversation's messages. The imported_ tables and setting_pinned_items are untouched. The window's delete button says the Conversations go too.
  • Rebinding a Run from a local- id to the game's id is an UPDATE run_tracker_runs SET id, and the four child tables follow. When a Run with the new id already exists, the two are merged in code instead, and the Conversations move to it (Rebinding a Run's id).
  • Deleting a Scraped run removes its cards, picks and combats. The _stats tables are not tied to a Scraped run; the importer works them out again.

Migrations and backups

MIGRATIONS is a list of SQL batches. Migration N takes a file from user_version N−1 to N, in one transaction with the version bump. An older file runs only the ones it lacks; a file newer than the app is refused with Error::NewerSchema. New migrations go at the end, and one that has shipped is never changed. Rows 1–7 name the tables as those migrations wrote them, before the prefixes.

Backup before migrating. When History::open finds a file with data (version above 0) behind the app, it first copies it with VACUUM INTO to history.v<N>.bak.db beside it (.bak.2.db, .bak.3.db, … if taken), where N is the old version. The copy is the file as it was; the app never removes it. To go back to an older build, close the app and put the copy in place of history.db.

GameData.db (read only)

The app also reads the game's own GameData.db to name cards, but never writes it and does not own its schema. CardCatalog copies the file first and opens the copy with SQLITE_OPEN_READ_ONLY, reading the cards table (Id, Data). See card-catalog-and-art.md.

Inspecting the file

Open it read-only while the app or just tracker track is running, so nothing typed can write to it:

-- sqlite3 -readonly .bazaar-tracker\history.db
PRAGMA user_version;          -- 9
.schema
SELECT name, type FROM sqlite_master WHERE name NOT LIKE 'sqlite_%' ORDER BY type, name;
PRAGMA foreign_key_check;     -- should return nothing
