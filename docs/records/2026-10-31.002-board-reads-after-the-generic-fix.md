# Board reads after the generic-instance fix

## What was discussed

This is a rerun of `just snapshot -- --watch` after the fix recorded in `2026-10-31.001-first-run-against-the-game.md`, where `GENERICINST` now resolves through `MonoGenericClass.cached_class`. It was the same Unranked run as Jules: day 2, a shop after an encounter choice, one loss so far. A screenshot of the game screen was taken during the run to check the values against. The raw output is at the end.

## Results

- **The board reads work.** All 11 polls succeeded with no detach. Before the fix, every board read failed and the tracker detached every five polls.
- **Checked against the screenshot:**

  | Value | Snapshot | Screen |
  |---|---|---|
  | Health | 400 / 400 | 400 |
  | Gold | 14 | 14 |
  | Income | 5 | +5 |
  | Level | 2 | 2 |
  | Day | 2 | 2 (the clock) |
  | Player board | 4 items (2 Small, 2 Medium) plus 1 socket effect | 4 cards (2 small, 2 medium) |
  | Shop offer | 3 `itm_` ids in the `Encounter` state | 3 cards for sale |
  | Skills | 1 | 1 skill icon |
  | Record | 0 victories, 1 loss | — |

  The record is consistent with the last combat, which the opponent won (winner 1, loser 0).
- **Run state.** It moved from `Choice` (3 `enc_` ids on offer, hour 0) to `Encounter` (3 `itm_` ids, hour 1) as the player picked an encounter.
- **Card details.** Tier, size, socket, enchantment (`Toxic`), tags (`Food`, `Tool`) and the attribute dictionaries all read. The `Dictionary` and `HashSet` readers work on the real game.
- **Opponent stats.** These still showed the last PvP opponent (Mak) while in a shop. That matches `<SimPvpOpponent>` and the opponent attributes keeping their last values.

## Decided

- Ticket 11's board reading is confirmed on a shop screen.
- Ticket 11 stays `ready-for-human` until the board has been seen during a PvE and a PvP combat, including opponent board positions, and the remaining open questions below are answered.

## Open questions

- **`frame_count` is still 665**, the same as in both combats of record `.001`. The combat reader very likely reads a stale or wrong `Frames` list. Check it after the next fight.
- **Attribute `100=0`.** Every item has an attribute keyed `100` that has no name, so `ECardAttributeType` value 100 is missing from the enum table (the `GameEnums` table or the baked fallback).
- **Admin rights.** Still not recorded whether attaching works without them.
- **Combat boards.** The opponent board and slots during combat have not been checked yet.
