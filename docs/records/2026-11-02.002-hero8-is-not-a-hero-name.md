# `Hero8` is not a hero name

## What was discussed

Settings → Item odds shows a hero button labelled `Hero8`. Nobody sees a hero called that in the game. The discussion covered three questions: where the name comes from, which steps of the tracker it reaches, and whether separate `in_game_name` and `display_name` fields (with a fallback) would fix it.

## Where `Hero8` comes from

The name comes from the game itself. The tracker does not invent it. The game's `EHero` enum names value 8 `Hero8`, probably an internal placeholder that was never renamed. The game then writes that enum name as text in its own data. A check of a copy of `prod/cache/GameData.db` on 2026-11-02 found:

- **`cards` table.** 486 cards have `"Hero8"` in `Heroes`, next to the real names (`Common` 1345, `Vanessa` 552, `Dooley` 540, `Pygmalien` 531, `Mak` 509, `Karnok` 490, `Jules` 466, `Stelle` 446). Samples: *Aila Chibi*, *Dragon Statue*, *Freiya's Package*, *Mittel's Package*, *Bass*.
- **`collectibles` / `hero_skin`.** One skin has `HeroId: "Hero8"`: **"Explosive Debut Dragons"**. Every other skin carries its hero's real name (for example "Primal Pyg" for `Pygmalien`).
- **`level_ups`.** Spawn prerequisites list `"Heroes": ["Dooley","Jules","Hero8"]`.
- **No display name anywhere.** No table in `GameData.db` maps `Hero8` to a display name. A plain-text search of `translations/*.bytes` and `Player.log` found nothing either. The name the player sees must come from somewhere else, such as the client's localisation or UI assets, which the tracker does not read.

The tracker gets `Hero8` from two independent places, and today both give the same string:

1. **Memory.** `crates/bazaar-tracker/src/enums/mod.rs:48` has a built-in `EHero` table, copied from the original tracker's fallback (`docs/rea/bazaar-tracker/memory-reading.md` §5): `8 => "Hero8"`. The number read from memory is turned into text with `hero::name_or_raw`.
2. **Card catalog.** `crates/bazaar-tracker/src/catalog/mod.rs:148` copies each card's `Heroes` strings as they are. `src/tracking/item_odds.rs:287` (`heroes()`) builds the Settings buttons from those strings, and `src/ui/odds_load.rs:182-187` uses each string as both the key and the label.

Because the two strings match, the matches between the hero read from memory and the hero named on a card work. That is a good thing. The only problem is the label.

## Where `Hero8` reaches the tracker

| Step in the game | Where in the tracker | What uses the string |
|---|---|---|
| Hero picked, run starts | `memory/game.rs:632-645` (`read_selected_hero_state`), `run/lifecycle.rs:112` | `RunStarted.hero`, then `runs.hero` in `history.db` |
| Every board read during the run | `memory/game.rs:556` (`stats.hero`) | `LiveView.hero` (`src/tracking/live.rs:137`), board view (`src/tracking/run/board.rs:226`) |
| Run list and Run header | `src/tracking/session.rs:195`, `src/tracking/run/header.rs:52` | Shown as is: "Hero8" |
| Encounter choice (merchants) | `src/ui/item_odds.rs:333` → `choice_groups` | Key for saved odds (`ItemOddsBook::get(template_id, hero, tier)`) |
| Tracked items pop-up | `src/ui/item_odds.rs:412-415, 512` | Key for odds, plus the text "Tracked in this run, as Hero8." |
| Combat against a player who plays Hero8 | `memory/game.rs:626` (PvP opponent), `run/combat.rs:142` | `CombatStart.opponent_hero` in events and in the narrated log |
| Settings → load many items' odds | `item_odds::heroes`, `item_odds::load_queue` (`item.heroes.contains(hero)`) | Button label and key; matched against catalog `Heroes` |
| Asking Bazaar DB | `crates/bazaardb/src/webview/item_odds.rs:11` (`page_for`) | Sent as `?hero=Hero8` |
| Saving Bazaar DB's answer | `src/tracking/item_odds.rs:96-100` (`accept`) | Saved under the hero **Bazaar DB's answer** names, not under the one asked for |

The game also uses `Hero8` in its `level_ups` spawn rules. The tracker does not read those, so they do not affect it.

## Can `in_game_name` and `display_name` separate them?

Yes. The two names do different jobs, and only one of them is broken:

- **`in_game_name`** (`Hero8`) is the **key**. It is what memory gives (through the enum table), what cards' `Heroes` say, and what is already stored in `history.db` (`runs.hero`, `item_odds.hero`, the event JSON). It must stay unchanged everywhere data is stored or compared. Swapping it for a display name would break the match with the catalog and would orphan the rows already saved.
- **`display_name`** is only for **showing**: Settings buttons, the Run list, the Run header, the Tracked items text, and the combat log. It is mapped from the key at the UI boundary only.

**Fallback chain:** `display_name` → `in_game_name` → raw number. Concretely:

- If the hero has a known display name, show it.
- Otherwise, show the game's string, as today. For a future `Hero9`, that means the label is ugly but nothing breaks.
- If the enum number itself is unknown, show the number. `name_or_raw` already does this.

The mapping can live next to the `hero` enum as a small table, for example `display_name("Hero8") -> Some("…")` and `None` for every hero whose game name is already its display name.

There is a third name to watch: **Bazaar DB's hero name**. It is not known whether bazaardb.gg expects `hero=Hero8` or some other name for this hero. This matters because `accept()` saves the odds under the hero named in **Bazaar DB's answer**. If Bazaar DB answers with a different string, the odds are saved under that string. Then every lookup by `Hero8` misses, so the odds never show, and every load writes the note "they are for X, not Hero8". If the names differ, map them both ways at the Bazaar DB boundary (`page_for` going out, `accept` coming back), so that storage keeps using `in_game_name`.

## Decided

- The cause is the game: `EHero` value 8 is named `Hero8`, and the game writes that name into its own data. It is not a tracker bug in reading.
- Keep `Hero8` (the in-game name) as the stored and compared key everywhere. Add a display name only for what is shown, with the fallback display name → in-game name → number.

## Open questions

- **What is Hero8's display name?** The skin "Explosive Debut Dragons" and the dragon-themed cards point to the hero known as **the Dragons**. A Mobalytics guide calls the Dragons "the eighth Hero to be released" and mentions *Scorch*. Neither name was checked in the game's own UI. Read it off the hero select screen before writing it into the table.
- **What name does Bazaar DB use for this hero** in `?hero=` and in its answer's `hero` field? Check with one request before the Settings bulk load is run for it. If they differ, the existing code saves the odds under the wrong key (see above).
- Should the display name map be built in, or editable in `settings.toml` so the next placeholder hero can be fixed without a release? *Answered in [Hero display names](2026-11-05.001-hero-display-names.md): built in.*
