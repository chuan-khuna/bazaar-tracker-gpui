macOS support

5 November 2026 · branch feat/macos-support · commit 64f65b2

What was discussed

Whether the app, which is built for Windows, runs on macOS, and then whether it can track the game on macOS without breaking the Windows build. The Bazaar has a native macOS build on Steam (TheBazaar.app, universal x86_64 + arm64). This Mac (Apple silicon, macOS 27) has the game installed.

Decided

  • Port the memory reader and keep one code path. Only the process access, the module listing and the export lookup depend on the platform. The Mono walk (mono::class, field, statics, value, bcl) runs through the Memory trait and is shared as it is.
  • Windows code moves but does not change. mem/process.rs and mem/module.rs become thin shared modules. The Windows code lives as it was in process_windows.rs and module_windows.rs, and the macOS code in process_macos.rs and module_macos.rs. Every switch is cfg(windows) or cfg(target_os = "macos").
  • No root. The tracker is ad-hoc signed with com.apple.security.cs.debugger. The game is ad-hoc signed without the hardened runtime, so task_for_pid succeeds for a user in the _developer group.
  • A separate offsets table for macOS, measured on the live game, not guessed.

Finding the root domain (unityspy-rs/src/mono)

  • mono::macho (new): the Mach-O counterpart of mono::pe. It reads the header and load commands at the dylib's load address, finds __TEXT, __LINKEDIT and LC_SYMTAB, and looks up _mono_get_root_domain in the symbol table, adding the slide. Everything is read from the game's memory, so the slice of the universal file that is actually running is the one read.
  • domain::root_domain decodes three forms, checking the bytes before it trusts any displacement: 
    Windows x64   48 8B 05 <rel32> C3                      mov rax,[rip+rel32]; ret
macOS x64     55 48 89 E5 48 8B 05 <rel32> 5D C3        push rbp; mov rbp,rsp; mov rax,[rip+rel32]; pop rbp; ret
macOS arm64   adrp x8, page ; ldr x0, [x8, #imm] ; ret     (the game: adrp x8,498 ; ldr x0,[x8,#0xe98])
  • MONO_MODULE is libmonobdwgc-2.0.dylib on macOS. Mono::attach picks pe or macho, and for_version or for_macos_version, by platform.

How the class shift was confirmed: in a dumped MonoClass, +0x38 pointed to the TheBazaarRuntime image, +0x40 was the name (<UpdateGemsWithDelay>d__8), +0x50 was a TypeDef token (0x02000c30), +0xB0 pointed back to the class with type code 0x11 (VALUETYPE, right for a release-build state machine), and +0xF8 held a field count of 4.

Bazaar layer and app

  • bazaar-tracker: memory::game and Tracker::start_live are built on macOS too. PROCESS_NAME is The Bazaar on macOS. keyring gains apple-native, so an upload key would go to the Keychain.
  • log::path: user_profile() reads HOME outside Windows. default_path_in and game_folder_in give the macOS log and card-data folders (they are two different folders on macOS).
  • App: the tracking service starts on macOS. A release build keeps its data in ~/Library/Application Support/BazaarTracker/.

Signing

  • macos/entitlements.plist: only com.apple.security.cs.debugger.
  • macos/sign.sh ad-hoc signs a binary with it. macos/run.sh is Cargo's runner on macOS (.cargo/config.toml): it signs, then runs. So cargo run, just run, the examples and the tests are all signed with no extra step.
  • justfile: [macos] versions of build (which signs the release binary) and app. The Windows recipes are marked [windows] and are otherwise unchanged.
Tried first: task_for_pid from an unsigned binary on an ad-hoc target returns KERN_FAILURE (5). The same binary signed with the entitlement gets the port and reads memory, without root.

Checked

Windows-only tests (Credential Manager, kernel32.dll version, Windows paths) are cfg(windows). Open questions

  • The whole workspace has not been built on Windows. A cross-check from macOS stops at ring's C build, which needs the Windows SDK headers. Only unityspy-rs was cross-checked. Build and test on Windows before merging (just test, just spike).
  • Not yet tried during a run. The snapshot was taken at the hero choice, so the board, stash, shop, combat result and PvP opponent reads are unproven on macOS. Play a run with just track or the app.
  • Vtable statics (vtable 0x48) read correctly for TheBazaar.Data and the rank. BoardManager.Instance was "not initialised" outside a run, which is expected, but should be checked during one.
  • x86_64 macOS (Intel, or Rosetta) is untested. The decoder knows its form; the offsets are assumed to be the same as on arm64.
  • Still Windows only: the Bazaar DB web view panel (WebView2) and the card-art extractor's game-folder check (TheBazaar_Data; on macOS the data is in TheBazaar.app/Contents/Resources/Data).
  • On macOS the window opened on the second display (x = −1466). The sidebar's empty-state text is clipped. Neither was looked into.
