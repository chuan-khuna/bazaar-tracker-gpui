What was discussed

We want an agent, the Advisor, that you can ask about the build you have now: which item to pick, which items work together, which shop to visit, how to arrange the Board, and which skill to take. It should answer from two sources:

  • Game knowledge: the card catalog (GameData.db: tier, size, heroes, description and attributes) plus the Shop odds and item odds the app already keeps.
  • Scraped runs: the runs scrape-runs saves in .bazaar-tracker/raw_data/scraper/builds/, each with its final Board and skills and its full timeline of what was offered and what was taken.

The first version of this record looked at how agents are built in D:\code\learning-agent (apps/tau-app) and proposed a FastAPI backend with a Next.js chat. A grilling session later the same day settled the open questions: the chat lives inside the gpui app, and there is no Next.js. This record is the revised proposal. The spec and tickets are in .scratch/build-advisor/.

How tau-app builds an agent

apps/tau-app runs agents on tau's Python libraries: tau_agent runs the loop and the tools, and tau_ai streams from OpenRouter. FastAPI serves the API and keeps history in SQLite. These are the parts worth copying:

tau-app's main rule carries straight over: the model never invents data. Every count, rate and odds number comes from a tool, and the model explains and weighs those numbers.

There is no current_build tool: the situation comes with each message and is in the prompt. Every tool returns its sample size (n) and the seasons it used. The prompt says to show a number only with its sample size, and to say the data is thin under 10 runs.

A tool, as in tau-app

Built with tau-app's define_tool. The numbers come from knowledge/; the tool only checks the arguments and hands the result back as JSON.

from agents.core.tooling import define_tool
from knowledge import synergy as stats

MIN_RUNS = 10  # below this, the reply says the data is thin


async def _synergy(args: dict) -> dict:
    cards = [name.strip() for name in args["cards"] if name.strip()]
    if not cards:
        raise ValueError("Give at least one card name.")
    sample = stats.sample(hero=args.get("hero"), min_runs=MIN_RUNS)  # current season, plus the previous one when thin
    partners = stats.partners(cards, sample, limit=args.get("limit", 8))
    return {
        "cards": cards,
        "partners": [
            {"card": p.card, "runs_together": p.n, "run_ids": p.run_ids, "lift": round(p.lift, 2), "shared_mechanics": p.shared_keys}
            for p in partners
        ],
        "seasons": sample.seasons,
        "runs_looked_at": sample.size,
        "thin": sample.size < MIN_RUNS,
    }


synergy = define_tool(
    name="synergy",
    description="The cards most often on a final Board with these cards, per hero: lift, runs together, shared mechanics.",
    properties={
        "cards": {"type": "array", "items": {"type": "string"}},
        "hero": {"type": "string"},
        "limit": {"type": "integer"},
    },
    required=("cards",),
    run=_synergy,
)

Opening it

  • A chat icon on a Run in the sidebar (shown on hover and on the selected Run): selects the Run, opens the Detail island on the Advisor tab, and shows that Run's newest Conversation, or starts one if it has none.
  • A chat icon on the Main island, next to the pop-out button: the same for the Live run. It's greyed out when no Run is live.
  • Switching Runs keeps the open tab. The open tab isn't saved.
  • When the backend isn't running, the tab says so and names just advisor serve. It tries again when you send.

Conversations

  • The list shows the selected Run's Conversations, newest first. Each is titled with the first words of its first question and the Day and Hour it was asked.
  • + starts a new Conversation on the Run. ✕ (on hover) deletes one after you confirm.
  • While a reply is coming in, Send becomes Stop. Stopping keeps what arrived, marked "Stopped".

A reply

  1. Thinking status: a pulsing Thinking… 4s, which becomes a collapsed Thought for 6s that opens to the thinking text.
  2. Tool calls: one muted line each, with a spinner, then ✓ or ✕. Collapsed by default; opened, it shows the arguments and the result as JSON.
  3. Answer text as it streams, with light markdown (bold, lists, inline code). Tables stay plain text.
  4. The recommendation card, where the Advisor called suggest.
  5. Suggested questions: 2–3 buttons from follow_ups. Clicking one sends it.
  6. Usage: one muted line: model, time, tokens, cost, tool count. Hovering shows input, output, cache, cost and time.

ask_user is drawn as a question with option buttons (and a text box when allowFreeText). After it's answered it is locked, with the pick highlighted, rebuilt from the next user message as tau-app does.

Synergy from cards appearing together

Treat each Scraped run's final Board plus skills as one basket of cards. For each pair of cards A and B, within one hero and the season sample:

MeasureFormulaShows
Supportn(A∧B)How much data there is. Drop pairs below a minimum, for example 5.
LiftP(A∧B) / (P(A)·P(B))Whether players put them together more often than chance. Above 1 means they're built together.
Win-rate gainmean wins | A∧B − mean wins | A onlyWhether adding B to A goes with better results
Smoothed rateBeta prior: (wins + α) / (n + α + β)Keeps one 10-win run from topping the list

The season sample: the current season's runs for the hero. When there are fewer than 10, the previous season's are added, and every result names the seasons it used (S20 (8 runs) + S19 (20 runs)).

Do the same for adjacent pairs, using slotPosition and size on the final Board, for arrangement, and for card-then-card in the timeline for pick order. The importer works these out into imported_pair_stats, imported_pick_stats and imported_adjacency_stats, so a tool call is a quick query.

Two cautions about the data.
  1. It's small. Today the builds folder holds 1 profile and 16 runs. Pair stats need hundreds of runs per hero. Scrape feeds for each hero and several profiles first.
  2. It's biased toward winners. A ?by=wins feed lists only strong runs, so the win-rate gain has nothing to compare against. Lift still works, as "what good players build together". For a win-rate signal, also scrape whole profiles (losses included).
Co-occurrence shows what is built together, not why. Game mechanics (shared attribute keys, description text) give the reason, and the model combines the two.

Database

Everything goes in history.db, beside the tracker's tables, following the prefixes from 2026-11-08.002. The tracker app owns the schema: migration 9 adds the tables below, and the file is backed up first as every migration does. The backend opens the file with WAL and busy_timeout, checks user_version against the version it was written for, and refuses a file it doesn't know. It writes only advisor_* and imported_* rows other than the odds, and never run_tracker_*.
