What was discussed

We want a chat agent you can ask about the build you have now: which item to pick, which items work together, which shop to visit, how to arrange the Board, and which skill to take. It should answer from two sources:

  • Game knowledge: the card catalog (GameData.db: tier, size, heroes, description and attributes) plus the Shop odds and item odds the app already keeps.
  • Scraped run history: the runs scrape-runs saves in data/scraper/builds/, each with its final Board and skills and its full timeline of what was offered and what was taken.

The stack we asked for: a FastAPI backend, the agent's own source, a frontend (Next.js, or a panel inside the gpui app), and a database to be decided later, perhaps Postgres loaded from the scraped data. This record looks at how agents are built in D:\code\learning-agent (apps/tau-app) and proposes how to build this agent the same way.

Decided (as asked)

  • Backend: FastAPI. The agent runs inside it and streams replies.
  • Agent: its code lives in src/agents/, laid out one folder per agent as in tau-app.
  • The agent decides from the item database and game mechanics, plus scraped run history.
  • Synergy can be found from items appearing together in builds.
  • Frontend: Next.js or inside gpui (not yet chosen). Database: not yet chosen; maybe Postgres, loaded from the scraped data.

How tau-app builds an agent

apps/tau-app runs agents on tau's Python libraries: tau_agent runs the loop and the tools, and tau_ai streams from OpenRouter. FastAPI serves the API and keeps history in SQLite. The UI is the separate Next.js app apps/chat. These are the parts worth copying:

tau-app's main rule carries straight over: the model never invents data. Matcha's prompt says "only use what the tools return". Here that means every count, rate and odds number comes from a tool, and the model explains and weighs those numbers.

Every tool returns its sample size (n). The prompt says to show a number only with its sample size, and to say "not enough data" when it is under a threshold, for example fewer than 10 runs.

A tool, as in tau-app

Built with tau-app's define_tool. The numbers come from knowledge/; the tool only checks the arguments and hands the result back as JSON.

from agents.core.tooling import define_tool
from knowledge import synergy as stats

MIN_RUNS = 10  # below this, the reply says the data is thin


async def _synergy(args: dict) -> dict:
    cards = [name.strip() for name in args["cards"] if name.strip()]
    if not cards:
        raise ValueError("Give at least one card name.")
    partners = stats.partners(cards, hero=args.get("hero"), limit=args.get("limit", 8))
    return {
        "cards": cards,
        "partners": [
            {"card": p.card, "runs_together": p.n, "lift": round(p.lift, 2), "shared_mechanics": p.shared_keys}
            for p in partners
        ],
        "runs_looked_at": stats.run_count(args.get("hero")),
        "thin": stats.run_count(args.get("hero")) < MIN_RUNS,
    }


synergy = define_tool(
    name="synergy",
    description="The cards most often on a final Board with these cards, per hero: lift, runs together, shared mechanics.",
    properties={
        "cards": {"type": "array", "items": {"type": "string"}},
        "hero": {"type": "string"},
        "limit": {"type": "integer"},
    },
    required=("cards",),
    run=_synergy,
)

A Jules run. The Board has Giant Lollipop (Large) and Pizza Cutter (Small). A merchant offers Decanter, Laurel's Bouncy Ball and Cheese Wheel.

Lift = n(A and B) × N / (n(A) × n(B)), with N = 15. "Picks" counts timeline selection events, so one offer seen twice counts twice.

The reply

You: Which of these should I take?

→ current_build · rate_options(Decanter, Laurel's Bouncy Ball, Cheese Wheel) · synergy(Giant Lollipop, Pizza Cutter) · arrangement(…)

Advisor: Take Laurel's Bouncy Ball. It's the only option that shows up with both of your items: alongside Giant Lollipop in 3 of 5 Jules runs, and alongside Pizza Cutter in 3 of 4 (lift 2.8). Decanter is close behind with Pizza Cutter (3 runs), but it shows up with Giant Lollipop only twice. Cheese Wheel gets taken a lot when offered (11 of 15), but it's rarely on a Board with your two items.

Where to put it: it's Small, so it fits. In the saved runs Giant Lollipop sits in the middle (slots 1–4), and Pizza Cutter sat right next to it in 2 runs. Keep those two together and put the Ball on the free side.

How sure: not very. This is 15 runs from one player, all wins, so it shows what one strong player builds rather than what wins more. For a skill, Quick Freeze was the most common one with Giant Lollipop (3 of 5).

Synergy from cards appearing together

Treat each scraped run's final Board plus skills as one basket of cards. For each pair of cards A and B, within one hero and one season:

MeasureFormulaShows
Supportn(A∧B)How much data there is. Drop pairs below a minimum, for example 5.
LiftP(A∧B) / (P(A)·P(B))Whether players put them together more often than chance. Above 1 means they're built together.
Win-rate gainmean wins | A∧B − mean wins | A onlyWhether adding B to A goes with better results
Smoothed rateBeta prior: (wins + α) / (n + α + β)Keeps one 10-win run from topping the list

Do the same for adjacent pairs, using slotPosition and size on the final Board, for arrangement. Do it for card-then-card in the timeline (what was taken after what) for pick order. Work these out once in the importer, into tables (pair_stats, pick_stats, adjacency_stats), so a tool call is a quick query.

Two cautions about the data.
  1. It's small. Today data/scraper/builds/ holds 1 profile and 16 runs. Pair stats need hundreds of runs per hero. Scrape feeds for each hero and several profiles first.
  2. It's biased toward winners. A ?by=wins feed lists only strong runs, so the win-rate gain has nothing to compare against. Lift still works, as "what good players build together". For a win-rate signal, also scrape whole profiles (all of a player's runs, losses included) or a feed that isn't sorted by wins.
Co-occurrence shows what is built together, not why. Game mechanics (shared attribute keys, description text) give the reason, and the model combines the two.

Database

Start with SQLite through SQLAlchemy and Alembic, as tau-app does. It needs no server, one file sits beside the data, and the same models move to Postgres by changing the database URL. Move to Postgres when someone other than you uses the agent, or when the data outgrows one file. SQLite can query the scraped JSON well into the tens of thousands of runs.

Frontend

  1. First, the Next.js chat. Reuse apps/chat from learning-agent, or copy it. It already renders streamed thinking, tool calls and ask_user cards against this exact API, so the UI costs nothing at the start.
  2. Later, inside gpui: a Widget or a side island that calls the same POST /api/conversations/{id}/messages and reads the SSE stream. The window then knows the Live run without a tool call: it can send the build with the message, and show answers next to the Board. The backend stays the same; only the client changes.

Build order

  1. Data: scrape the feeds for each hero, plus some whole profiles.
  2. Importer and knowledge/: load cards, runs, picks and odds, work out the stats, and test them with pytest. No LLM yet.
  3. Agent in the terminal: ADVISOR with find_card, synergy and rate_options, run through cli.py. Tune the prompt on real questions.
  4. FastAPI and SSE: copy tau-app's backend, and point the Next.js chat at it.
  5. Live build: current_build from history.db, and put it into the prompt through prepare.
  6. The rest of the tools: shop_plan, arrangement and similar_runs.
  7. A gpui panel: built on the same API.

Open questions

  • Privacy: a model on OpenRouter would receive your Board and run history. Run data is meant to stay on this machine. Use a local OpenAI-compatible model (the provider only needs a different base_url), send only card names, or accept OpenRouter for this?
  • Card ids: do Bazaar DB's baseId UUIDs (in summary.items[].cardId and on the Board) match the card Id in GameData.db? If they don't, the importer matches on names.
  • Where the build comes from: the agent can read history.db itself (read-only, so the app stays the one writer), or the gpui app can send the build with each message. Either way, pasting a build should also work.
  • Folder: app/advisor/src/agents/, as proposed, or another place?
  • Seasons: should stats use only the current season (after a patch) or pool seasons with older ones weighted less?
  • Database: SQLite first and Postgres later, or Postgres from the start?
