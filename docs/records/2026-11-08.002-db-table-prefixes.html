What was discussed

Today history.db has seven tables with bare names (runs, events, shop_odds, item_odds, tracked_items, hidden_items, pinned_items). The names say what a row is, not where it came from, and the file is about to grow: the build advisor record (2026-11-08.001) wants card data from the game and scraped builds beside the tracker's own Runs. We asked for a new layout with every table prefixed by its module:

  • run_tracker_: what the tracker records while you play.
  • game_db_: data read straight from the game's files.
  • imported_: data brought in from outside: builds, item odds, Shop odds, meta and the like.
  • setting_: the player's own choices.

The rule

A table's prefix says where its rows come from, and so what it costs to lose them. That decides how each group is cleared, backed up and refreshed:

PrefixRows come fromIf lostRefreshedWriter
run_tracker_Player.log and memory reads, as you playGone for good; the only copyNever; only added toThe tracker
game_db_The game's install folder (GameData.db)Nothing; rebuilt from the gameWhen the game's file changesThe catalog loader
imported_Bazaar DB, the scrapers' files, built-in defaultsFetched or imported againOn Refresh or ImportThe importers
setting_The player, in the windowChosen again by handWhen the player changes themThe window

Two more rules keep the groups apart:

  • Foreign keys stay inside a prefix. run_tracker_events may point at run_tracker_runs, but nothing points into game_db_ or imported_, because those are dropped and refilled whole. Across prefixes, tables join by value (a template id, a hero name).
  • Every imported_ table says where each row came from, in a source column, and when, in imported_ms. Then a re-import can replace one source's rows and leave the others.

Proposed schema

run_tracker_

The tables keep their columns; only the names change. These are the rows that cannot be got back, so they are the ones a backup must cover.

CREATE TABLE run_tracker_runs (
    id          TEXT PRIMARY KEY,
    started_ms  INTEGER NOT NULL,
    ended_ms    INTEGER,
    ended       INTEGER NOT NULL DEFAULT 0,
    hero        TEXT,
    day         INTEGER,
    victories   INTEGER,
    losses      INTEGER,
    outcome     TEXT
);
CREATE INDEX run_tracker_runs_by_start ON run_tracker_runs (started_ms);

CREATE TABLE run_tracker_events (
    seq          INTEGER PRIMARY KEY AUTOINCREMENT,
    id           TEXT NOT NULL UNIQUE,
    run_id       TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    kind         TEXT NOT NULL,
    timestamp_ms INTEGER NOT NULL,
    day          INTEGER,
    hour         INTEGER,
    details      TEXT NOT NULL
);
CREATE INDEX run_tracker_events_by_run ON run_tracker_events (run_id, timestamp_ms, seq);

CREATE TABLE run_tracker_tracked_items (
    run_id      TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    added_ms    INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

CREATE TABLE run_tracker_hidden_items (
    run_id      TEXT NOT NULL REFERENCES run_tracker_runs(id) ON DELETE CASCADE ON UPDATE CASCADE,
    template_id TEXT NOT NULL,
    hidden_ms   INTEGER NOT NULL,
    PRIMARY KEY (run_id, template_id)
);

game_db_

Today CardCatalog reads GameData.db (from a copy) into memory on every start, and nothing else can query it. Saving it as a table lets SQL join card names onto Events, odds and builds, and lets the advisor and the scrapers read the same cards. The tables are a cache: the loader compares the game file's size and modified time with game_db_source, and when they differ it empties both tables and fills them again in one transaction.

-- One row: which game file the cards were read from.
CREATE TABLE game_db_source (
    id           INTEGER PRIMARY KEY CHECK (id = 1),
    path         TEXT NOT NULL,     -- the GameData.db that was read
    file_size    INTEGER NOT NULL,
    modified_ms  INTEGER NOT NULL,  -- the file's modified time
    game_version TEXT,              -- the exe's FileVersion, when known
    read_ms      INTEGER NOT NULL
);

CREATE TABLE game_db_cards (
    id            TEXT PRIMARY KEY, -- the template id, lower-cased
    name          TEXT NOT NULL,
    type          TEXT NOT NULL,    -- Item, Skill, EventEncounter, …
    size          TEXT,             -- Small, Medium, Large
    starting_tier TEXT,
    heroes        TEXT NOT NULL,    -- JSON array; ["Common"] for neutral
    description   TEXT,
    attributes    TEXT,             -- JSON object
    data          BLOB              -- the row as the game stores it, for fields not split out yet
);
CREATE INDEX game_db_cards_by_name ON game_db_cards (name);

Card art stays as files under art/; images do not belong in the database.

imported_

Everything from outside the game and the player. The two odds tables move here. Scraped builds join them when the advisor is built; their shape comes from the advisor record.

CREATE TABLE imported_shop_odds (
    day         INTEGER PRIMARY KEY,
    samples     INTEGER NOT NULL,
    bronze      REAL NOT NULL,
    silver      REAL NOT NULL,
    gold        REAL NOT NULL,
    diamond     REAL NOT NULL,
    source      TEXT NOT NULL,     -- 'bazaardb', 'builtin', 'file'
    imported_ms INTEGER NOT NULL
);

CREATE TABLE imported_item_odds (
    template_id TEXT NOT NULL,
    hero        TEXT NOT NULL,
    tier        TEXT NOT NULL,
    url_id      TEXT NOT NULL,
    item_name   TEXT NOT NULL,
    body        TEXT NOT NULL,
    source      TEXT NOT NULL,     -- 'bazaardb' (asked in the window), 'scraper' (Import item odds…)
    imported_ms INTEGER NOT NULL,
    PRIMARY KEY (template_id, hero, tier)
);

-- Later, for the build advisor: scraped runs from data/scraper/builds/.
CREATE TABLE imported_builds (
    run_id       TEXT PRIMARY KEY, -- Bazaar DB's run id
    profile_id   TEXT,
    hero         TEXT NOT NULL,
    season       INTEGER,
    created_ms   INTEGER,
    wins         INTEGER,
    losses       INTEGER,
    victory_tier TEXT,
    source       TEXT NOT NULL,    -- 'scraper'
    imported_ms  INTEGER NOT NULL
);
CREATE TABLE imported_build_cards (
    run_id   TEXT NOT NULL REFERENCES imported_builds(run_id) ON DELETE CASCADE,
    card_id  TEXT NOT NULL,
    kind     TEXT NOT NULL,        -- 'board', 'skill'
    tier     TEXT,
    slot     INTEGER,
    PRIMARY KEY (run_id, kind, card_id, slot)
);
CREATE TABLE imported_build_picks (
    run_id   TEXT NOT NULL REFERENCES imported_builds(run_id) ON DELETE CASCADE,
    day      INTEGER,
    hour     INTEGER,
    card_id  TEXT NOT NULL,
    tier     TEXT,
    taken    INTEGER NOT NULL
);

"Meta" (tier lists, popular builds, patch notes) gets an imported_meta_… table when there is a real source for it; no table is made ahead of the data.

setting_

CREATE TABLE setting_pinned_items (
    hero        TEXT NOT NULL,
    template_id TEXT NOT NULL,
    pinned_ms   INTEGER NOT NULL,
    PRIMARY KEY (hero, template_id)
);

settings.toml stays a file. Some of its keys (log_path, game_dir) are needed before the database opens, and a file can be edited by hand when the app will not start. setting_ tables are for choices that are lists and grow, like pinned items, which a TOML file holds badly.

Migration 8

One new entry at the end of MIGRATIONS; the seven that shipped stay as they are. The bundled SQLite (rusqlite 0.41 with bundled) is far past 3.26, so ALTER TABLE … RENAME TO also rewrites the REFERENCES in the child tables, and RENAME COLUMN is there. Indexes keep their old names after a table rename, so they are dropped and made again.

-- 8: prefix every table by where its rows come from.
ALTER TABLE runs          RENAME TO run_tracker_runs;
ALTER TABLE events        RENAME TO run_tracker_events;
ALTER TABLE tracked_items RENAME TO run_tracker_tracked_items;
ALTER TABLE hidden_items  RENAME TO run_tracker_hidden_items;
ALTER TABLE shop_odds     RENAME TO imported_shop_odds;
ALTER TABLE item_odds     RENAME TO imported_item_odds;
ALTER TABLE pinned_items  RENAME TO setting_pinned_items;

DROP INDEX runs_by_start;
DROP INDEX events_by_run;
DROP INDEX events_waiting_for_upload;
CREATE INDEX run_tracker_runs_by_start ON run_tracker_runs (started_ms);
CREATE INDEX run_tracker_events_by_run ON run_tracker_events (run_id, timestamp_ms, seq);
ALTER TABLE run_tracker_events DROP COLUMN upload_status;

ALTER TABLE imported_shop_odds RENAME COLUMN saved_ms TO imported_ms;
ALTER TABLE imported_shop_odds ADD COLUMN source TEXT NOT NULL DEFAULT 'bazaardb';
ALTER TABLE imported_item_odds RENAME COLUMN saved_ms TO imported_ms;
ALTER TABLE imported_item_odds ADD COLUMN source TEXT NOT NULL DEFAULT 'bazaardb';

CREATE TABLE game_db_source (…);   -- as above
CREATE TABLE game_db_cards (…);    -- as above
CREATE INDEX game_db_cards_by_name ON game_db_cards (name);

It runs in one transaction with PRAGMA user_version = 8, like every migration, so a failure leaves the file at 7. An app older than this one then refuses the file (NewerSchema), which is the existing rule. The imported_build… tables come in their own later migration, with the advisor.

Shop odds seeded from the built-in defaults get source = 'bazaardb' from the default above. If that matters, the migration can mark rows whose values equal bazaardb::shop_odds::defaults() as 'builtin', but it is simpler to let the next Refresh replace them.

Code layout

The Rust modules can follow the prefixes, so the file a table lives in is found from its name:

TodayProposed
history/mod.rs (Runs, Events, rebind, delete)store/run_tracker/: runs.rs, events.rs, tracked_items.rs, hidden_items.rs
history/shop_odds.rs, item_odds.rsstore/imported/: shop_odds.rs, item_odds.rs, later builds.rs
catalog/ (in memory)store/game_db/cards.rs; CardCatalog loads from it
history/pinned_items.rsstore/setting/pinned_items.rs
history/uploads.rsRemoved
history/schema.rsstore/schema.rs

The SQL that names a table is in 8 files today, about 40 statements besides the schema itself, all inside crates/bazaar-tracker/src/history/; nothing outside the crate writes SQL against history.db. The rename is mechanical, and the existing tests cover every table.

Clear data in Settings can then offer the groups separately: clear runs, clear imported data, rebuild game data, reset settings.

Decided

  • Prefix every table by module: run_tracker_, game_db_, imported_, setting_.
  • game_db_ holds only what is read straight from the game; imported_ holds everything from outside (builds, item odds, Shop odds, meta).

Open questions

  • Pinned items: setting_pinned_items (a choice that outlives Runs), as proposed, or run_tracker_pinned_items?
  • Tracked and hidden items: they are player choices too. Keep them under run_tracker_ because they belong to one Run and cascade with it, or move them to setting_ and give up the foreign key?
  • Upload column: the upload feature is to be removed (2026-11-02.001). Drop upload_status in migration 8, or leave it until the upload code goes?
  • File name: history.db no longer says what is in it. Rename it (for example bazaar-tracker.db), moving the old file on first start, or keep the name?
  • One file or several: one file with prefixes, as proposed, or game_db_ and imported_ in their own files joined with ATTACH, so a backup copies only the tracker's file? The prefixes make a later split easy either way.
  • Moving the catalog into the database: part of this change, or a later one? The renames alone need no new code.
