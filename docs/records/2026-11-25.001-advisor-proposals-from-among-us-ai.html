25 พฤศจิกายน 2026 · branch feat/advisor-game-knowledge · ต่อจาก Among AI: agent ตัดสินใจจาก state ของเกมอย่างไร · สภาพปัจจุบันของ Advisor อยู่ใน Advisor message flow และ advisor.md · เป็นข้อเสนอ ยังไม่ได้ตัดสินใจ · คำที่ขีดเส้นประ ชี้เพื่อดูความหมาย

สรุปสั้น ๆ

among-us-ai เก่งเพราะส่งให้โมเดลเฉพาะสิ่งที่ต้องใช้ตัดสินใจ ณ จังหวะนั้น ในรูปที่เลือกได้ทันที: เหตุที่ถูกปลุก, ภาพตอนนี้, log ส่วนตัวที่ไม่ทิ้งหลักฐาน, รายการ action ที่ทำได้จริงพร้อม label ที่คำนวณไว้แล้ว และ schema ต่อ state Advisor ของเรามีส่วนแรก ๆ อยู่แล้ว (situation เหนือคำถาม, ตัวเลขมาจาก tools เท่านั้น, ตัดผล tool เก่าทิ้ง) แต่ยังขาดห้าเรื่อง: ไม่รู้ว่า Run ที่ผ่านมาเกิดอะไร, ไม่รู้ว่าอะไรซื้อได้จริง, ต้องเรียก tool หลายรอบก่อนตอบ, ทุก stage ได้คำสั่งเหมือนกัน และไม่เคยเรียนรู้จากผลของ Run

ข้อเสนอ

1. Run log: สิ่งที่เกิดใน Run นี้ P1

ลอกจาก
EpisodicMemory และ renderLog(limit): N บรรทัดล่าสุดเต็ม, เรื่องปกติที่เก่ากว่าย่อเป็น route, evidence ไม่ถูกตัด
ตอนนี้
situation เป็นภาพนิ่ง Advisor ไม่รู้ว่าผู้เล่นแพ้ PvP สองครั้งติดให้ Board สาย Poison, เพิ่งขายของ หรือชนะมาแล้วกี่ครั้ง จึงแนะนำเหมือนทุก Run เริ่มที่ Hour นี้

ทำอย่างไร: backend สร้าง run log จาก run_tracker_events ของ Run ที่ Conversation ผูกอยู่ (Advisor อ่าน history.db ได้อยู่แล้วตาม ADR 0002) แล้ว render เป็นส่วน ## This Run so far ใต้ situation หนึ่ง Event ต่อบรรทัด มี [D H] กำกับ

## This Run so far (Jules, Ranked · record 3 wins, 1 loss · Prestige 17)
[D1–D3] took: Pizza Cutter, Giant Lollipop, Stove · chose: Chris Army, Pyro · rerolled ×2   ← เรื่องปกติที่เก่า ย่อเป็นบรรทัดเดียว
[D3 H6] PvP vs Vanessa (Lv 5; Pufferfish, Poison Dagger, …): Win, Health 1100 → 420
[D4 H6] PvP vs Pygmalien (Lv 6; Shield-heavy): Loss, Health 1200 → 0

ตัวอย่างประกอบ ชื่อคู่แข่งและตัวเลขสมมุติ ทุกบรรทัดมาจาก EventKind ที่ tracker บันทึกอยู่แล้ว

  • evidence ไม่ถูกย่อ: CombatEnd (พร้อม Board คู่แข่งสั้น ๆ จาก CombatStart), Sold, การ upgrade (merged_into) และการเปลี่ยนสายของ Board ส่วน Selected, encounter ที่เลือก และ Rerolled ที่เก่ากว่า Day ก่อนหน้า ย่อเป็นบรรทัด took / chose / rerolled ×n
  • ไม่รั่วอนาคต: เมื่อผู้เล่นแนบ Event เก่า (situation.event) log ต้องหยุดที่ Event นั้น เหมือน test ของ among-us-ai ที่ fail เมื่อ prompt มีสิ่งที่ seat นั้นไม่ควรรู้ ควรมี test แบบเดียวกัน
  • history: log เป็นส่วนหนึ่งของ question message จึงถูกจัดการเหมือน situation: คำถามเก่าที่ situation ต่างไปแล้วไม่ต้องส่ง log เก่าซ้ำ (ดู ข้อ 3 เรื่องเก็บคำถามแยกจากส่วนที่ render)
  • ทางเลือก: ให้แอปส่ง run_log มาใน situation แทน ง่ายต่อ Run ที่ยังไม่ถูกบันทึก แต่ต้องแก้ schema ทั้งสองฝั่ง และ situation จะใหญ่ขึ้นทุก Event แนะนำให้ backend อ่านเอง

ไฟล์: knowledge/ (query ใหม่อ่าน run_tracker_events), agents/advisor/history.py (question_message รับ run id), backend/agent/runner.py (ส่ง run id ของ Conversation), กฎใหม่ใน prompts/system.md: "use the Run so far: what beat the player, what they sold, their record"

2. Legal actions: ตัวเลือกที่ทำได้จริง พร้อม id P1

ลอกจาก
legalActions() ที่มีแต่ action ที่ทำได้ตอนนี้ (kill:Kimi มีเฉพาะเมื่อ cooldown 0) และ matchAction(): exact → normalize → prefix ยาวสุด → fallback
ตอนนี้
suggest รับชื่อการ์ดที่โมเดลพิมพ์ จับคู่ชื่อได้ แต่ไม่ตรวจว่าเงินพอไหม มีที่วางไหม และไม่มีตัวเลือก "ไม่ซื้อ", "reroll" หรือ "ขายก่อนแล้วซื้อ" Board read มี BuyPrice และ SellPrice อยู่ใน Item.attributes แต่ situation ไม่ได้ส่งมา

ทำอย่างไร:

  1. แอปเพิ่ม price ให้การ์ดใน Offer และ sell_price ให้การ์ดบน Board และ Stash (schema ใน situation.py และ situation.rs)
  2. backend สร้าง legal actions จาก situation: buy:<name> (เงินพอ), sell:<name>, sell-then-buy:<sold>><bought> เมื่อเงินหรือที่วางไม่พอแต่ขายแล้วพอ, reroll, leave, take:<encounter>, pick:<skill> ชื่อซ้ำต่อท้าย #2
  3. label บอกผลที่ต้องรู้ เหมือน (walk to Electrical (~9s)): ราคา, เงินที่เหลือ, ใช้กี่ช่อง, ช่องว่างหลังซื้อ, ไปอยู่ Board หรือ Stash
  4. suggest รับ ranked[].action แทน card จับคู่แบบ matchAction() และ action ที่ทำไม่ได้เป็น ValueError ที่บอกเหตุผล ("buy:Cheese Wheel costs 9 gold, the player has 6") เหมือน engine ที่ปฏิเสธ action แล้วเขียน Could not do …

3. เตรียมตัวเลขก่อนถาม P1

ลอกจาก
among-us-ai ใส่ข้อมูลที่ต้องใช้ตัดสินใจไว้ใน label แล้ว โมเดลตอบได้ใน model call เดียว
ตอนนี้
กฎใน system.md บอกลำดับเดิมทุกครั้ง: rate_options → synergy → suggest → ข้อความ → follow_ups เป็นงานที่ backend รู้ล่วงหน้าทั้งหมด แต่จ่ายเป็น model call ละรอบ

ทำอย่างไร: ก่อน model call แรก backend รัน tool ที่ stage นั้นต้องใช้เสมอ (ข้อ 5) แล้วใส่ผลแบบย่อลงใน label ของ legal actions

- buy:Laurel's Bouncy Ball  (6 gold → 6 left; Small → 5 free; on 4 of 15 final Boards; taken 7 of 15 times offered;
                             with Giant Lollipop 3 of 5 (lift 2.25), with Pizza Cutter 3 of 4 (lift 2.81))
- buy:Cheese Wheel          (9 gold → 3 left; Medium → 4 free; offered 17 times; never on a final Board with Giant Lollipop)
Numbers: 15 Jules runs · S20 · 1 profile.

ตัวเลขของ Bouncy Ball และ Cheese Wheel มาจาก Scraped runs 16 run ของวันที่ 8 พฤศจิกายน ตามที่ advisor.md บันทึกไว้ ราคาสมมุติ

  • โมเดลยังเรียก rate_options, synergy, find_card ได้ถ้าอยากรู้มากกว่านี้ แต่กรณีปกติเหลือ suggest + ข้อความ + follow_ups (หรือรวมเป็นหนึ่ง call ถ้า provider ยอมให้เรียกหลาย tool ใน turn เดียว)
  • กฎ "ตัวเลขทุกตัวมาจาก tool พร้อม n" ยังจริง: ตัวเลขใน label มาจาก knowledge/ ชุดเดียวกัน แค่ถูกเรียกโดย backend
  • history ต้องแก้: ตอนนี้ question message ที่เก็บไว้มี situation ที่ render แล้วฝังอยู่ ส่วนที่เตรียมไว้ (และ run log) จะอยู่ในนั้นด้วย เมื่อ situation เปลี่ยน model_history ต้องตัดส่วนเหล่านี้ของคำถามเก่าออก เหมือนที่ตัดผลของ SITUATION_TOOLS อยู่แล้ว วิธีที่ง่ายสุดคือเก็บข้อความคำถามดิบกับ situation แยกกัน แล้ว render ใหม่ทุกครั้ง
  • system prompt และ tool definitions ยังเหมือนเดิมทุก byte cache จึงยังได้ผล

คาดว่าได้: model calls ต่อคำถามแบบ "ซื้ออะไรดี" จาก ~5 เหลือ 2–3 ซึ่งเป็นเงื่อนไขของ ข้อ 7 ด้วย (ถ้าจะปลุกเองทุก Offer ต้องเร็วและถูก) ตัวเลขจริงวัดด้วย replay bench และ step stats ที่มีอยู่

4. Replay bench: วัดก่อนแก้ P1

ลอกจาก
simulator ที่ใช้ brain ชุดเดียวกับเกมจริง และ test/match.test.js
ตอนนี้
tests ตรวจว่า tools คืนตัวเลขถูก แต่ไม่มีอะไรบอกว่า prompt ใหม่ทำให้คำแนะนำดีขึ้น เร็วขึ้น หรือถูกลง

ทำอย่างไร: ใช้ Run ของผู้เล่นเองใน history.db ซึ่งมี Snapshot ทุก Event แอปมี for_event ที่สร้าง situation ณ Event หนึ่งอยู่แล้ว

  1. tracker export situation ของทุก OptionsPresented ใน Run ที่เลือก เป็น JSONL (เช่น just tracker situations <run>) พร้อมสิ่งที่ผู้เล่นเลือกจริง (Selected ที่มี options_event_id ตรงกัน) และผลของ Run
  2. just advisor bench file.jsonl --model … ถาม "What should I do?" ทีละ situation (run log ตัดที่ Event นั้น) แล้วเก็บผล
  3. รายงาน: action ที่แนะนำ legal ไหม, invalid และ refusal, จำนวน model calls, เวลา, ค่าใช้จ่าย, ตรงกับที่ผู้เล่นเลือกกี่ครั้ง และตรงกับที่ strong runs เลือกในวันเดียวกันกี่ครั้ง (day_picks)

"ตรงกับที่ผู้เล่นเลือก" ไม่ได้แปลว่าถูก แต่เมื่อแยกตาม Run ที่ชนะและแพ้จะเห็นแนวโน้ม และใช้เทียบ prompt สองแบบบนชุดเดียวกันได้ ใช้ --fake ใน CI เพื่อตรวจเฉพาะส่วนที่ไม่ขึ้นกับโมเดล (legal, isolation, จำนวน call)

ลอกจาก

ตอนนี้

  • เก็บในตารางใหม่ advisor_run_plans ซึ่งต้องเป็น migration 10 ใน crates/bazaar-tracker/src/history/schema.rs เพราะ tracker เป็นเจ้าของ schema และ Advisor ต้องรับ user_version 10

  • ค่าใช้จ่าย: setting advisor.auto = off | offers | all (ค่าเริ่ม off), งบสูงสุดต่อ Run และแสดงใน usage line

Glossary

คำของโดเมน (GLOSSARY.md)

Advisor
agent ที่ผู้เล่นถามเรื่อง build ได้: เลือกไอเทมไหน, อะไรเข้ากัน, ไปร้านไหน, จัด Board อย่างไร, เลือก skill ไหน ตอบจาก card catalog, odds และ Scraped runs
Run
การเล่น The Bazaar หนึ่งรอบ ตั้งแต่เลือก hero จนชนะหรือแพ้
Event
สิ่งหนึ่งที่เกิดขึ้นใน Run และถูกบันทึกไว้ เช่น มีตัวเลือกเสนอมา, เลือกไอเทม, combat เริ่มหรือจบ
Snapshot
Board, Stash, skills และค่าสถานะของผู้เล่น ณ ขณะหนึ่งของ Run บันทึกไว้คู่กับ Event
Board
ไอเทมที่ผู้เล่นใช้งานอยู่ วางบน 10 ช่อง: Small ใช้ 1 ช่อง, Medium 2 ช่อง และ Large 3 ช่อง
Stash
ไอเทมที่ผู้เล่นถือไว้ แต่ไม่ได้วางบน Board
Offer
การ์ดที่เกมเสนอให้ผู้เล่น ณ ขณะหนึ่ง ให้ซื้อ รับ หรือเลือก ได้แก่ไอเทมของ merchant, loot หรือตัวเลือกของ encounter
Conversation
ข้อความชุดหนึ่งระหว่างผู้เล่นกับ Advisor เกี่ยวกับ Run เดียว Run หนึ่งมีได้หลาย Conversation

คำในเอกสารนี้

Situation
JSON ที่แอปส่งไปกับทุกคำถาม บอกสภาพเกม ณ ตอนนั้น: hero, Day, Hour, gold, Board, Stash, skills, Offer และ opponent เป็นภาพนิ่ง ไม่มีสิ่งที่เกิดก่อนหน้า
Decision point
จังหวะที่ agent ถูกปลุกให้ตัดสินใจ ใน among-us-ai คือ order เสร็จหรือมีเหตุการณ์มาขัด ข้อเสนอนี้ใช้ Event ของ tracker เป็น decision point
Wake reason
เหตุที่ Advisor ถูกถาม ณ ตอนนี้ (asked, offer_opened, combat_lost …) เขียนเป็นบรรทัดแรกของคำถาม เหมือน You are deciding now because …
Run log
บันทึกสิ่งที่เกิดใน Run นี้จนถึงตอนนั้น สร้างจาก Event ของ tracker หนึ่งบรรทัดต่อ Event เรื่องปกติที่เก่าย่อรวม ผล combat และการขายไม่ถูกย่อ
Legal actions
สิ่งที่ผู้เล่นทำได้จริงตอนนี้ (buy, sell, reroll, leave, take, pick) แต่ละตัวมี id ให้โมเดล copy และ label ที่บอกราคา เงินที่เหลือ และช่องว่าง
Stage
ช่วงของเกมที่ backend คำนวณจาก situation: shop, encounter, loot, skill, combat, after_combat หรือ free แต่ละ stage มีตัวเลขที่เตรียมไว้ คำสั่ง และสิ่งที่ reply ต้องจบด้วย
แผนของ Run
core, wanted, avoid และเงื่อนไขเปลี่ยนสาย ที่ Advisor บันทึกด้วย set_plan หนึ่งชุดต่อ Run และใส่ในทุกคำถามถัดไป
Lesson
โน้ตไม่เกิน 3 ประโยคที่ Advisor เขียนถึงตัวเองหลังจบ Run ต่อ hero เป็นความเห็น ไม่ใช่สถิติ
Replay bench
ชุดวัดที่ถาม Advisor ซ้ำที่ทุก Offer ของ Run ที่บันทึกไว้ แล้วนับ action ที่ทำไม่ได้, model calls, เวลา, ค่าใช้จ่าย และความตรงกับสิ่งที่เลือกจริง
